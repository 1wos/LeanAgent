## 슬라이드 구성

### 1. Autoformalization: 컴파일 성공에서 의미 충실성으로
- **핵심 메시지**: Lean이 코드를 받아들인다는 것과 원래 수학 문제를 정확히 옮겼다는 것은 다르다.
- **내용**:
  - 자연어 수학 명제·증명 → Lean 4 형식 언어
  - 질문: 무엇을 올바른 번역으로 볼 것인가?
  - 조사 범위: 목록 내 8편 + 목록 밖 추가 조사 10편
- **발표 메모** (40초): 이번 발표는 논문별 나열보다 데이터, 피드백, 평가 기준이 어떻게 연결되는지에 집중한다. 추가 10편은 원문에서 2026-10-10 abstract 확인으로 표시한 자료다.
- **원문 근거**: 1장, 6장

### 2. 왜 LeanAgent의 앞단이 중요한가?
- **핵심 메시지**: 번역한 statement가 틀리면 증명이 성공해도 원래 문제를 해결한 것이 아니다.
- **내용**:
  - 전체 흐름: 문제 이해 → Lean statement 생성 → 증명 → 검증
  - 연구의 세 축: 병렬 데이터·번역 / 검증 피드백 / 프로세스·평가
  - 평가 대상 확장: statement → 정리+증명 → 전체 파이프라인
- **발표 메모** (55초): prover 실패와 statement 오류를 구분해야 한다는 문제의식을 먼저 공유한다. 세 축은 조사 내용을 설명하기 위한 묶음이며 논문 간 배타적인 분류는 아니다.
- **원문 근거**: 1장, 3장, 5장

### 3. Herald: 병렬 데이터는 어디서 오는가?
- **핵심 메시지**: 자연어→Lean 데이터가 부족하면 Mathlib4를 자연어로 옮겨 학습 쌍을 만든다.
- **내용**:
  - Mathlib4 → 자연어 역방향 번역
  - tactic·informal 이중 증강, Lean-jixia 분석기
  - Herald Translator: miniF2F-test statement 형식화 Pass@128 93.2%
  - 자체 대학원 교과서 데이터셋: 22.5%
- **발표 메모** (70초): 핵심은 높은 점수 자체보다 데이터 확보 전략이다. 두 수치는 서로 다른 평가셋의 결과이므로 동일 조건의 난이도 비교나 모델 순위로 해석하지 않는다. TheoremLlama 50.1%는 Herald 비교표의 보조 근거이며 이번 개요에서는 직접 검증한 성능처럼 다루지 않는다.
- **원문 근거**: 2.1절, 3.1절

### 4. PDA: 컴파일러 피드백을 과정 감독으로
- **핵심 메시지**: 성공한 출력만 고르는 대신 오류 피드백의 내용을 학습 신호로 활용한다.
- **내용**:
  - FormL4: Mathlib4 자연어화 + 수작업 검수, out-of-domain real 셋 포함
  - 생성 → Lean 피드백 → 과정 라벨 → PSV 학습 → autoformalizer 재학습
  - 비교: 컴파일 성공분만 학습하는 RFT
  - GitHub README 기준 basic 셋 형식화 정확도: 40.92 → 46.28
- **발표 메모** (70초): PSV는 Process-Supervised Verifier다. 원문은 abstract 외에 공식 README로 세부 구성을 보강했다. basic 셋의 보고값을 다른 논문의 pass@k와 같은 척도로 비교하지 않는다.
- **원문 근거**: 2.2절, 3.2절

### 5. NL2Lean / ReLean: 컴파일 보상만으로는 부족하다
- **핵심 메시지**: 의미·하위항·구조·컴파일을 함께 보상해야 의미 충실성을 다룰 수 있다.
- **내용**:
  - LLaMA3-8B 기반 번역기 + 다면 보상 PPO + 쉬운 것→어려운 것 커리큘럼
  - 네 보상: 의미 정렬 / term 정렬 / 전체 구조 정렬 / REPL 컴파일 체크
  - 컴파일되면서 의미도 맞는 비율: Lean Workbook 26.6%, ProofNet 19.2%
  - 한계: 의미 평가에 사람 annotation 사용
- **발표 메모** (75초): 컴파일 보상 단독으로는 의미 충실도가 확보되지 않았다는 ablation이 중요하다. 수치는 컴파일률이 아니라 의미까지 맞는 statement 비율이다. 사람 판정 비용도 함께 기억한다.
- **원문 근거**: 2.3절, 3.3절

### 6. ProofBridge: statement에서 증명 전체로
- **핵심 메시지**: 검색과 반복 수정으로 정리+증명을 번역하고 타입 정확성과 의미 정확성을 분리한다.
- **내용**:
  - joint embedding으로 formal 예시 검색 → retrieval-augmented fine-tuning → 반복 proof repair
  - 수정 신호: Lean 타입 체커 + 의미 등가 피드백
  - TC: 타입 체크 통과 / SC: 양방향 equivalence 증명으로 확인한 의미 일치
  - miniF2F-Test-PF, pass@32: Kimina-Prover-RL-1.7B 대비 SC +31.14%p, TC +1.64%p
- **발표 메모** (75초): SC의 큰 개선은 해당 논문의 비교 조건에서 나온 상대 차이다. 절대 성공률이나 다른 데이터셋 대비 우위로 바꿔 말하지 않는다. 의미 검증에도 추가 증명 작업이 필요하다.
- **원문 근거**: 2.4절, 3.2~3.3절

### 7. 벤치마크도 검증 대상이다
- **핵심 메시지**: formal–informal 불일치는 전체 파이프라인 평가를 흔든다.
- **내용**:
  - Evaluation Benchmark(04): 복잡한 수학 영역에서 당시 LLM의 한계를 드러냄
  - miniF2F-Lean Revisited: 오류·불일치·단순화를 고친 miniF2F-v2 공개
  - 개별 단계 최고 성적: 형식화 97%, 증명 69% ≠ 전체 성공률
  - 원문 요약의 전체 성공률 약 36%, v2 70% — 기준 확인 필요
- **발표 메모** (75초): 원문 2.5절은 약 36%를, 4장 표는 40% → 70%를 제시한다. 이를 임의로 하나의 전후 비교로 통합하지 않는다. 해당 기준은 추후 원문 확인이 필요하다. 단계별 최고 수치의 조건도 같다고 가정하거나 곱해 전체 성능을 추정하지 않는다.
- **원문 근거**: 2.5절, 4장

### 8. 숫자를 읽는 법: 지표·조건을 먼저 보기
- **핵심 메시지**: 논문별 성능 수치를 하나의 순위표로 합칠 수 없다.
- **내용**:
  - 컴파일률: 컴파일되는 비율 / 정확도: 컴파일되면서 의미도 맞는 비율
  - pass@k: k개 샘플 중 하나라도 성공할 확률 — k와 성공 기준을 함께 표시
  - TC·SC / 파이프라인 성공률은 측정 대상이 다름
  - 확인 항목: 데이터셋·버전·번역 대상·판정 기준·샘플 수
  - 예: Herald Pass@128, ProofBridge pass@32, NL2Lean 사람 판정 정확도는 직접 비교 불가
- **발표 메모** (75초): miniF2F v1/v2, statement와 증명 전체, 컴파일과 의미 판정을 구별한다. 조사 원문이 모든 논문의 조건을 동일 수준으로 제공하는 것은 아니므로 수치가 없는 조건을 채워 넣지 않는다.
- **원문 근거**: 4장 및 각 핵심 논문 결과

### 9. 2026 추가 조사①: 충실성·견고성 평가
- **핵심 메시지**: 최근 조사 자료는 '같은 정리인가'와 '입력 변화에도 충실한가'를 더 직접적으로 묻는다.
- **내용**:
  - Beyond Compilation: 컴파일률–충실성 격차 1.3~29.5%p 보고
  - SHADOWBENCH / SA-Pass: 보조 명제의 순·역방향 함축 검사
  - The Faithfulness Gap / BPF: 순·역방향 귀결 지문으로 의미 표류 검출
  - Robustness 연구: 전역·국소 교란에 대한 증명 형식화 평가
  - Paraphrase-Induced Failures: 같은 의미의 표현 변화가 유발하는 실패 분류
- **발표 메모** (80초): 5편은 원문의 abstract 요약 수준에서 소개한다. 격차 수치는 시스템별 결과이지 일반적인 오류율이 아니다. SA-Pass·BPF는 정합성 검사 후보이며, 우리 프로젝트에서 검증된 구현이라는 뜻은 아니다.
- **원문 근거**: 6.1절, 추가 시사점

### 10. 2026 추가 조사②: 파이프라인에서 연구 논문으로
- **핵심 메시지**: 검색·국소 수정과 장기 진행 관리가 더 큰 형식화 작업으로 이어진다.
- **내용**:
  - MathForm: 생성 전 Mathlib 검색 + 생성 후 컴파일·의미 피드백, FormalVerse 데이터 구축
  - DSR: 논리 성분 분해 → 연산자 트리 → 하위 트리 단위 수정

  - LeanMarathon: 공유 blueprint 중심 4에이전트 하니스
  - Pistis: 원문 논증 구조의 충실성, 반증 탐색으로 증명 간극 발견
- **발표 메모** (80초): 5편의 개별 성능을 나열하지 않고 작업 단위가 커지는 흐름에 집중한다. 연구 수준 사례는 W12 use case의 참고 자료이지 임의의 연구 논문을 자동 형식화할 수 있다는 보장은 아니다. 추가 10편의 papers.md 등록 여부는 원문에서 합의가 필요한 후보로 남아 있다.

### 11. LeanAgent 적용: 실패를 구분하는 검증 루프
- **핵심 메시지**: 먼저 무엇이 실패했는지 기록해야 다음 수정 전략을 고를 수 있다.
- **내용**:
  - statement 정합성 점검으로 번역 오류와 prover 실패 구분
  - 컴파일·타입 체크와 의미 판정을 별도 기록
  - 오류 메시지 유형화 → 다음 시도 선택·반복 repair
  - 병렬 예시 검색을 활용한 few-shot 비교 실험
  - 컴파일 결과·pass@k·시간·비용 자동 기록, 사람 판정은 소표본
  - 벤치마크 버전과 성공 판정 기준 명시
- **발표 메모** (85초): 모두 원문 5장의 적용 제안이며 구현 완료를 뜻하지 않는다. SA-Pass·BPF는 의미 검사 후보, blueprint와 반증 탐색은 장기 연구 use case의 참고 아이디어로 구분한다. 자동 로그가 의미 판정을 대체하지는 않는다.
- **원문 근거**: 5장, 6장 추가 시사점

### 12. 결론과 남은 확인 사항
- **핵심 메시지**: 좋은 autoformalization은 '검증 가능한 코드'를 넘어 '원문에 충실한 형식화'여야 한다.
- **내용**:
  - 세 가지 요약: 병렬 데이터 확보 / 검증 피드백 활용 / 의미·전체 파이프라인 평가
  - TheoremLlama(05): abstract 미확인, papers.md 설명 + Herald 비교표만 근거
  - SOS(33): abstract 미확인, papers.md 설명 + 제목만 근거; 세부 추정 금지
  - miniF2F 원판 문항 수 미확인, 약 36%와 40%의 보고 기준 확인 필요
  - 토론: 우리 harness에서 번역 오류와 증명 실패를 어떻게 분리해 기록할까?
- **발표 메모** (30초): 미확인 항목은 결론의 근거로 확대하지 않는다. 논문 링크는 원문 7장을 참고하며, 발표에서는 지표 비교의 조건과 의미 충실성이라는 공통 질문을 남긴다.
- **원문 근거**: 1장 근거 상태, 2.5절, 4장, 7장 비고
