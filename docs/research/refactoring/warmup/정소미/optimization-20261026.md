# Warmup 15 · 증명 최적화와 검증 실험

2026-10-26 · 정소미

15문제의 검증된 출발 증명을 고정하고, 증명 길이와 컴파일 비용을 줄이는 새 후보를 실제로 실행했다. 명제와 원문 전체 문맥을 유지한 상태에서 후보를 만들고, 컴파일 오류나 Lean의 경고를 받아 수정한 뒤 재검증했다. 최종 선택은 토큰 수와 HB 감소율의 동일 가중 평균으로 결정했다.

기존에 확보한 좋은 증명을 출발점으로 사용하되, 이 문서의 **추가 개선**은 그 출발점에서 새로 줄어든 부분만 뜻한다. 원본 대비 누적 개선과 이번 실험의 기여를 합쳐서 세지 않는다. 출발 증명의 작성자·원본 파일·커밋과 이전 변경 경로는 [출처 목록](evidence/warmup15-20261026/starting-manifest.json)에 보존했다.

## 하나의 실행 흐름

[실행 코드와 재현 방법](evidence/warmup15-20261026/README.md)에 후보 생성과 검증을 묶었다. 입력을 바꾸지 않은 상태에서 각 문제의 제한된 편집을 재생성할 수 있다. 검사기는 기존 고정 평가기를 재사용한다.

1. 출발 증명·명제·라이브러리 버전·평가기를 해시로 고정한다.
2. 문제 구조에 맞는 국소 편집, 기존 정리 재사용, 중복 증명 공유를 적용한다.
3. 원문 전체 파일을 Lean으로 검사한다. 실패하면 실제 오류를 바탕으로 한정된 수리를 시도하고 실패 기록도 보존한다.
4. 유망한 후보는 원본·출발 후보와 같은 조건에서 각각 새 프로세스 3회 측정한다.
5. 채택할 후보는 지정 버전에서도 확인한다. 평균 점수 증가와 지정 버전 통과를 함께 만족하지 못하면 출발 후보를 유지한다.

paperthin은 작업 범위 확인(`readchk`), 기존 검사기 재사용(`ponytail`), 계측 독립성 점검(`mandela`), 제출 자료 재검토(`sip`)에 사용했다. 후보의 정당성을 에이전트의 동의로 결정하지 않는다. Lean의 결과와 보존한 측정값으로 판단한다. 무작위 후보 생성을 대량 호출하거나 학습된 라우터를 재현한 실험은 아니다.

## 실제로 적용한 방법

| 범위 | 시험한 변경 | 검증에서 확인할 점 |
|---|---|---|
| P01–P04 | 불필요한 정규화 항목 삭제, 귀납 증명 안의 패턴 축약·직접 항 구성, 예상 타입 명시 | 짧아져도 자동화 비용이 늘 수 있으며, 귀납 가정의 형태가 달라지면 실패한다. |
| P05–P06 | 미분 가능성 사실 공유, 불필요 `simp` 인수 삭제, 두 원소 조건의 직접 구성, 공통 보조정리의 정규형 변경 | P05의 C3 조건을 보존한다. P06의 비가환 대수에 가환 대수 법칙을 가져오지 않는다. |
| P07–P09 | 생성자를 직접 적용해 분기 닫기, 병렬 합류 증명 분해, 전이와 관계 증명 의무 분리 | P09 쌍모사의 두 방향을 모두 증명해야 한다. 구조를 분리한 후보가 길어지면 평균 점수에서 탈락할 수 있다. |
| P10–P12 | 기수 부등식의 기대 타입 명시, 인덱스 경계 정리 재사용, 두 fiber 평가 공유, 튜플 복원 정리 재사용 | 의존 타입의 인덱스를 보존하고, 같은 정리라도 목표 식의 표기를 맞춰야 한다. |
| P13–P15 | 산술 자동화를 기존 정리로 대체, 연속 재작성 결합, `ring1`과 직접 합 보존 증명 | 토큰 감소가 HB 증가를 상쇄하는지 고정된 비용식으로 비교한다. |

P05의 주요 이득은 마지막 대수 정규화를 제한한 데서 나왔다. 넓은 `simp` 호출을 아래처럼 필요한 규칙만 사용하는 `simp only`와 명시적 소거로 바꿨다. 별도로 통과했던 불필요 `Pi.sub_apply` 삭제도 결합해 다시 3회 검증했다. C3 가정과 원래 명제는 유지했다.

```lean
simp only [k, div_eq_mul_inv, pow_two, mul_inv_rev, one_mul,
  mul_assoc, mul_left_comm, mul_comm]
rw [mul_left_comm 𝓕.μ₀, mul_inv_cancel_left₀ 𝓕.μ₀_ne_zero]
```

P06에서는 두 방향의 교환관계가 나타났다. 공유 보조정리의 정규형을 바꾼 후보는 435토큰/HB 15,329로 짧아졌고, 두 원소 목록 조건을 직접 증명한 후보는 472토큰/HB 13,721로 HB가 낮아졌다. 둘 다 출발 후보 450토큰/HB 14,127보다 고정 평균 점수가 낮아 채택하지 않았다. 이번 탐색의 한계이며, 개선 가능성이 없다는 증명은 아니다.

P12의 수리 과정은 구체적인 예다. 수동으로 마지막 원소와 나머지를 분리하던 증명을 `Fin.snoc_init_self`로 바꿨다. 보조정리를 삭제하고 바로 재작성한 첫 시도는 `simp made no progress`로 실패했다. `← Fin.init_def`로 식의 표기를 먼저 맞추고 복원 정리를 적용한 수정본은 전체 문맥 검사에 통과했다. 실패한 첫 후보를 성공으로 소급하지 않고 각각 기록했다.

P11은 인덱스 경계의 수동 산술 증명을 기존 정리로 바꾸는 첫 후보에서 `Fin 2`의 0을 자연수로 읽는 타입 변환이 남아 실패했다. `Fin.val_zero`를 단순화에 포함해 실제 오류를 수리했다. 최종 선택은 `index-lemma-repair`이며 같은 증명으로 지정된 세 버전을 통과했다. 두 fiber 평가를 공유한 더 짧은 후보는 수리 후에도 등식 방향과 부분타입의 값 변환이 맞지 않아 실패로 기록했다.

## 문헌에서 가져온 범위

문헌의 전체 시스템을 구현했다는 뜻은 아니다. 이번 고정 문제와 비용 제약에서 실제 코드 변경으로 옮길 수 있는 부분을 선택했다.

- **LeanPolish**의 국소 교체·불필요 증명 제거 후 재검증 흐름과 **Lean Refactor**의 다목적 선택 원칙을 적용했다. P05의 제한된 단순화와 P07–P09의 작은 분기 변경도 전체 문맥 검증과 고정된 토큰/HB 기준을 거쳤다. [LeanPolish 원문](https://arxiv.org/abs/2609.38384), [Lean Refactor 원문](https://arxiv.org/abs/2605.20244)
- **Bidirectional Elaborators à la Carte**의 기대 타입을 이용한 정보 전달을 P03·P04·P10·P11의 직접 항 구성과 타입 명시에 연결했다. elaborator 자체를 구현하거나 해당 논문의 성능을 재현하지 않았다. [원문](https://arxiv.org/abs/2607.09564)
- **Recycling Algebraic Proof Certificates**에서 반복되는 증명 사실을 재사용한다는 아이디어를 가져와 P05·P06·P11·P12의 중복 보조 증명에 적용했다. 논문의 가환 대수 증명 체계를 비가환 Wick 대수에 그대로 적용하지 않았다. [원문](https://arxiv.org/abs/2507.20267)
- **LeanGraphSearch**는 가까운 관련 정리와 의존성을 찾아보는 방법의 참고로 사용했다. P12에서는 [고정 Mathlib의 `Fin.snoc_init_self` 선언](https://github.com/leanprover-community/mathlib4/blob/fabf563a7c95a166b8d7b6efca11c8b4dc9d911f/Mathlib/Data/Fin/Tuple/Basic.lean#L593)을 직접 확인했다. 검색 모델·임베딩·그래프 순위 시스템을 구현하지 않았다. [원문](https://arxiv.org/abs/2610.22339)
- 공통 합류 증명과 전이 의무의 분리 아이디어를 각각 P08·P09에서 시험했다. 원 논문의 Agda/PTS 및 Beluga/π-calculus 결과를 Lean의 SKI·CCS 정리로 대체한 것은 아니며, 이번 후보는 고정된 Lean 명제를 다시 증명해야 한다. [합류 관련 원문](https://arxiv.org/abs/2607.20188), [전이 관련 원문](https://arxiv.org/abs/2607.12652)
- 비용과 품질을 고려해 탐색을 중단하거나 다른 방법으로 전환하는 원칙을 적용했다. 논문의 토큰 비용 대용치와 이번 HB는 다르며, 논문의 학습된 정책이나 달러 비용 성능을 재현하지 않았다. [원문](https://arxiv.org/abs/2606.04883)

논문은 변경 방향의 근거다. 특정 변경이 유효하고 유리한지는 아래 실행 기록으로 판단한다. 실패와 퇴보 후보를 포함한 제한된 탐색이므로, 15문제 밖의 일반화나 모델 생성 성공률을 추정하지 않는다.

## 검증과 점수의 해석

공통 평가기는 `c18ec56682462847e2f4d8b6d60aa79ec071a10b`의 고정 코드다. 고정 명제, 원문 전체 문맥, 후속 선언과 허용 공리(`propext`, `Classical.choice`, `Quot.sound`)를 확인한다. HB는 공통 경로에서 원시 카운터를 1,000으로 나눈 내림값이다. 토큰은 LLM 사용량이 아닌 증명 본문의 구문 토큰이다.

`추가 점수 = 50 × ((출발 토큰 − 새 토큰) / 원본 토큰 + (출발 HB − 새 HB) / 원본 HB)`

선택에 쓰는 원본 분모와 출발 후보는 같은 실행 조건에서 측정한다. 서로 다른 버전이나 계측 경로의 HB를 섞지 않는다. P12는 유효한 유한 기수 `#(...)` 구문을 허용하는 기존 Somi full-source v2 경로이며 공통 14문제 평균에 넣지 않는다. 검증 실패, 환경 준비 실패, 미측정은 서로 구분한다.

문제당 $3 조건 충족은 확인하지 못했다. 별도 유료 생성 API는 호출하지 않았지만, 이 작업의 Codex 모델 호출 비용은 계측하지 않았다. 공개한 결과는 로컬 및 고정 CI 환경의 증명 실험이며 공식 Arena 제출 점수가 아니다.
