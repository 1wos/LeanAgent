# 중간 명제형 블록 전략: 규칙 기반 블록 분할과 조합 선택

중간 명제형은 `have`로 중간 사실을 세워 가며 결론에 이르는 증명으로, 최상위 블록 중 `have` 계열 블록이 토큰의 50% 이상인 경우임(Warm-up 4, 10–15번).

이 증명을 블록 트리로 나누고, 컴파일로 확인한 변경 후보 중 서로 겹치지 않으면서 proof token 감소가 가장 큰 조합을 고름. LLM은 쓰지 않으며 같은 입력이면 항상 같은 결과가 나옴. 4번(PhysLib)은 아직 실행 중이라 우선 10–15번만 정리해서 올림.

수치는 지정 버전에서 측정한 로컬 측정값임. 토큰은 공식 `proof_length` 규칙으로 세지만 공식 Arena 평가 결과는 아님.

## 규칙

1. 스택: 들여쓰기로 블록 트리를 만듦. 블록 하나 = 한 줄 + 그 아래 하위 증명.
2. DFS: 블록별 토큰 합을 구하고, 루트 합 + `:= by` 줄 토큰이 공식 `proof_length`와 같은지 확인함.
3. 해시: 지역 이름을 v0, v1, …로 바꿔 해시가 같은 블록(이름만 다른 중복)을 묶음.
4. 편집 거리 DP: 거의 같은 `have` 블록 쌍과 서로 다른 토큰(함수 인자 후보)을 기록함. 보고만 함.
5. 우선순위 큐: 예상 감소량이 큰 중복 그룹부터 보조정리로 묶어 컴파일해 봄.
6. 메모이제이션: 같은 파일 내용은 다시 컴파일하지 않음(`cache.json`).
7. 트리 DP: 서로 겹치지 않는 후보 조합 중 감소량이 가장 큰 것을 고르고, 한꺼번에 적용해 다시 컴파일함.

후보는 두 종류임.

- 미사용 블록 제거: `linter.unusedVariables.analyzeTactics`가 경고한 `have` 블록을 지우고 컴파일하는 과정을 경고가 없을 때까지 반복함([prune_unused.py](prune_unused.py)).
- 중복 블록을 보조정리로 묶기: 첫 멤버 자리에 `have blk_genK : ∀ (인자), 명제 := by …`를 두고 각 멤버를 `blk_genK 인자`로 바꿈. 예를 들어 15번의 `h₅`(d, e)와 `h₆`(e, f)를 `blk_gen1` 하나로 묶으면 748토큰이 줄어듦.

구현은 규칙 1–4가 [block_tree.py](block_tree.py), 5–7이 [block_dp.py](block_dp.py)임.

## 결과 (10–15번)

10–15번은 모두 웜업 문제이며, 10–12번은 ArkLib, 13–15번은 PutnamBench에서 온 문제임.

| 10 | ArkLib | `Binius.BinaryBasefold.fiberwise_dist_lt_imp_dist_lt_unique_decoding_radius` | 1,463 | 1,463 | 1,463 | 0.00% |

- 시작 토큰은 공식 `proof_length`와 같음.
- 모든 문제에서 원본과 최종 증명이 컴파일되고, 공리는 `propext`, `Classical.choice`, `Quot.sound`임.
- 13–15번은 트리 DP의 예측 감소량과 다시 센 감소량이 같음(48, 220, 955).
- 최종 증명은 `results/dpK/final.lean`에 있음. 후보별 컴파일 결과는 `cache.json`, 고른 조합은 `result.json`에 있음.

### 10–12번(ArkLib)에서 줄지 않은 이유

- 미사용 `have`: 린터 옵션을 켠 컴파일에서 "unused variable" 경고가 세 문제 모두 0건임. 같은 컴파일에서 다른 경고는 나오므로 린터는 동작함. Mathlib 스타일 검사를 거친 라이브러리 증명이라 쓰지 않는 `have`가 없는 것으로 보임.
- 중복 블록: 10, 11번의 중복 그룹 5개는 `have 이름 : 명제 := by` 한 줄 형식이 아님. 12번의 중복 그룹 2개는 tactic 블록 밖(항 자리, 예: `exact ⟨…, by …⟩` 안)에 있어 `trace_state`로 문맥을 읽을 수 없음.
- 같은 중간 명제형이라도 사람이 쓴 Putnam 풀이(13–15번)에서는 효과가 있고, 이미 다듬어진 라이브러리 증명(10–12번)에서는 이 규칙들로 줄일 부분이 없었음.

### 묶지 못한 중복 (13–15번)

14번 그룹 1–4는 다른 부분이 `A`/`Aᶜ` 같은 식이라 인자로 바꿀 수 없음. 14번 그룹 5와 15번 그룹 2·3은 `have 이름 : 명제 := by` 한 줄 형식이 아님.

## 신뢰구간

"이 규칙을 비슷한 문제에 적용하면 토큰이 평균 몇 % 줄어들까"를 지금까지 측정한 문제들로 추정한 범위임([reduction_ci.py](reduction_ci.py)). 문제 하나의 감소율을 표본 하나로 봄. 같은 문제는 다시 재도 값이 같으므로(컴파일과 토큰 수가 결정적), 범위의 폭은 문제마다 감소율이 다른 정도에서만 나옴.

| 측정한 문제 수 | 평균 감소율 | 95% 신뢰구간 (t 분포) | 95% 신뢰구간 (부트스트랩) |
| ---: | ---: | --- | --- |
| 6개 (10–15번) | 6.44% | −3.66%–16.53% | 0.45%–14.06% |

- 문제가 6개뿐이라 범위가 넓고, 참고용으로만 봐야 함. t 분포 구간의 하한이 0보다 작은 것도 표본이 적기 때문임(이 규칙은 토큰을 늘리지 않음).
- 출처에 따라 결과가 갈려(ArkLib 0%, Putnam 2.71–23.38%) 평균 하나로 요약하기 어려움.
- 4번까지 측정하면 문제 7개로 다시 계산할 예정.

## 환경과 한계

- 13–15번: Lean v4.26.0, Mathlib v4.26.0(커밋 `2df2f01`, [project/](project/)로 고정), 대회 데이터 header, `lake env lean`.
- 10–12번: ArkLib 커밋 `c1712f6`(v4.31.0), 저장소 원본 파일의 해당 줄만 바꿔 `lake lean`으로 컴파일하는 파일 모드. 실행 후 원본 파일은 바이트 단위로 복구됨.
- 린터가 일부 미사용 변수를 놓칠 수 있어(false negatives) 미사용 블록 제거 결과는 하한임.
- 보조정리로 묶기는 이름만 다른 블록, `have 이름 : 명제 := by` 한 줄 형식, tactic 블록 안의 멤버만 다룸.
- heartbeat는 재지 않음.

## 지난주에 이어 이번 주에 새롭게 추가한 아이디어

지난주에는 14, 15번 증명을 블록으로 나누고 블록 조합별 토큰을 잼. 이번 주에는 블록을 나누고 고르는 방법을 규칙으로 정해 자동화함.

- 중복된 블록은 하나로 통합하고, 재귀 함수처럼 블록을 함수 하나로 묶음.
- 스택, 해시, 큐 자료구조로 블록을 나누고 찾고 시도 순서를 정함.
- 블록 조합 선택은 DP로 함.
- 자동 단계는 미사용 `have` 반복 제거로 한정하고, 목표는 토큰만 봄(heartbeat 제외).
- 기대 효과는 문제 간 변동 기준 신뢰구간으로 냄.
