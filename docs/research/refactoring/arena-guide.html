01 / AGENT DEVELOPMENT

에이전트 개발 개요

Lean Refactor Arena에 참가할 증명 리팩터링 에이전트를 개발합니다. 문제를 이해하고 후보를 생성하는 단계부터, 검증 피드백을 통한 개선과 최종 제출까지 전체 흐름을 다룹니다.

개발 범위실행 흐름현재 구현과 연결 계약구현 문서

개선 목표: 원래 명제를 유지하면서 증명 토큰 길이와 Lean heartbeat를 줄입니다. 평가 하네스는 각 후보의 정확성과 개선 정도를 확인하고 다음 시도에 피드백을 제공합니다.

A1 / PROJECT SCOPE

문제 입력부터 최종 제출까지.

에이전트의 생성 전략, 실행 제어, 평가와 결과 분석을 하나의 실험 흐름으로 연결합니다.

  1. 01

    문제·실행 환경

    문제와 원본 증명, 주변 문맥을 준비합니다. Lean 버전과 의존성을 관리해 후보를 검증할 환경을 구성합니다.

  2. 02

    에이전트·리팩터링 전략

    모델 API와 도구를 연결합니다. 증명의 구조와 전략을 탐색하고, 개선 가능성이 있는 후보를 생성합니다.

  3. 03

    반복 실행 제어

    검증 결과를 다음 시도로 전달합니다. 오류 수정과 재시도, 호출 예산, 탐색 종료 조건을 관리합니다.

  4. 04

    평가·후보 선택

    반환된 중간 후보를 검증·측정하고 기록합니다. 탐색이 끝나면 최종 재검증을 거쳐 후보를 선택합니다.

  5. 05

    실험 분석·제출

    전략별 결과와 후보의 개선 이력을 비교합니다. 선택된 코드를 대회 제출 형식에 맞게 정리합니다.

프로젝트 전체의 개발 범위를 정리한 것으로, 모든 영역이 구현 완료된 상태를 뜻하지 않습니다.

A2 / AGENT WORKFLOW

생성하고, 확인하고, 다시 개선합니다.

전략은 후보 생성과 피드백 활용 방법을 결정합니다. 하네스는 반환된 후보를 측정·기록합니다.

PREPARE시작 준비

  1. 문제와 환경 준비

    원래 명제, 증명 문맥과 Lean 실행 환경을 입력으로 준비합니다.

  2. 원본 검증과 기준값 측정

    원본이 검증되는지 확인하고 토큰 길이와 heartbeat를 기록합니다.

ITERATE반복 개선

  1. 후보 생성

    API / agent가 리팩터링을 시도하고 측정할 중간 산출물을 반환합니다.

  2. 검증·측정·기록

    후보의 정확성을 검증하고 토큰 길이, heartbeat와 오류를 기록합니다.

  3. 피드백 반영

    개선 여부와 오류를 바탕으로 후보를 수정하거나 새로운 전략을 시도합니다.

피드백을 다음 후보 생성으로 전달 · 종료 조건에 도달할 때까지 반복

FINALIZE탐색 마무리

  1. 재검증과 최종 선택

    원본과 기록된 후보를 다시 평가하고, 검증과 선택 정책을 통과한 결과를 확정합니다.

  2. 제출 산출물 준비

    선택된 코드를 제출 형식에 맞게 정리하고 실험 기록과 연결합니다.

중간 측정을 실행 순서에 포함합니다. 현재 run_search()는 반환된 후보의 평가와 기록이 끝난 뒤 다음 propose(feedback)를 호출합니다. 측정할 중간 산출물마다 한 번 반환하도록 에이전트를 연결합니다.

A3 / IMPLEMENTATION

현재 구현과 다음 연결 지점.

구현 코드는 별도 Arena 리포에서 관리합니다. 평가 하네스에 생성 전략과 모델 API를 연결하고 대회 실행 흐름을 통합합니다.

현재 구현

평가 하네스와 연결 인터페이스

  • 원본 및 중간 후보 검증·측정
  • 후보 코드, 부모 후보, 측정 결과와 선택 사유 기록
  • 최종 재평가와 후보 자동 선택
  • Python 함수 및 JSON CLI adapter 연결

개발·통합할 영역

대회용 에이전트의 전체 실행

리팩터링 전략과 실행 정책을 평가 인터페이스에 연결해 실험할 수 있도록 구성합니다.

  • 모델 API 연동과 후보 생성 전략
  • 피드백에 따른 오류 수정과 탐색 전략
  • 호출 예산과 전체 실행 종료 조건 관리
  • 실험 결과 분석과 대회 제출 흐름 통합

에이전트가 연결되는 접점

Python에서는 propose(feedback)를 구현합니다. 별도 프로세스는 stdin / stdout으로 JSON을 주고받는 CLI adapter를 사용합니다.

입력
명제, 원본 측정값, 현재 최선의 코드, 직전 후보의 평가 결과
반환
후보 코드, 부모 후보 ID, 변경 의도 · 종료 시 None 또는 JSON null
기록
후보와 평가 결과를 매니페스트로 연결해 비교와 재현에 활용

현재 선택 기준은 로컬 실험용 점수입니다. 대회 공식 평가 및 제출 결과와는 구분합니다.

02 / FIXED ENVIRONMENT · PROPOSAL

문제별 환경 고정 가안

기존 Session·run_search 평가 흐름에 문제별 환경과 권한 경계를 추가하는 제안입니다. 환경 선택은 runner가 소유하며, API·sub-agent가 같은 문제와 지정 환경 목록에서 작업하도록 합니다.

구조도실험 결과검증 경계구현 순서근거와 재실행

논의용 가안입니다. OS 수준의 파일 읽기 격리, 실제 agent 통합, 공식 worker와의 채점 동등성은 아직 확인하지 않았습니다.

2대표 문제 · Strata / PutnamBench
4공식 지정 Lean 환경
24컴파일 실행 · 정상 20 / 오류 대조 4
0모델 API 호출

B1 / ARCHITECTURE

환경은 runner가 결정합니다.

고정 단위는 문제 → 공식 환경 목록 → 후보 해시입니다. 여러 버전이 지정되면 같은 후보를 모든 환경에서 검사합니다.

초록 · 파일럿에서 실행한 기능주황 · 추가 구현·통합회색 · 공식 입력

실선은 파일럿의 실행 경로, 점선은 제안하는 연결입니다. 초록색은 검증한 기능을 뜻하며 독립적인 운영 모듈이 모두 완성됐다는 뜻은 아닙니다. Registry는 기존 캐시를 확인했고, Linux 이미지 빌드는 수행하지 않았습니다.

B1 / BIND

문제와 환경 목록을 연결

Runner가 run_id에 문제와 환경 목록을 연결합니다. Agent 요청으로 compiler, cwd, 의존성 버전을 바꾸지 못하게 합니다.

B2 / INHERIT

자식에게도 같은 환경

Sub-agent는 같은 환경 목록과 도구 제한을 받습니다. 쓰기 가능한 작업 디렉터리는 실행별로 분리합니다.

B3 / TRACE

후보와 검증 근거를 연결

모든 결과에 문제·환경·후보 해시를 기록합니다. 다른 버전에서도 같은 후보를 검사하고, 환경 변경은 새 run으로 시작합니다.

B3 / VERIFIED BOUNDARY

어디까지 확인했는가.

환경 고정의 실행 가능성을 확인했습니다. 대회용 운영·격리의 승인 조건은 별도로 남겨 둡니다.

파일럿에서 확인

  • 잘못된 pin 거절. Lean 버전·저장소 commit 불일치를 실행 전에 차단했습니다.
  • 부모 환경변수와 분리. PATH, LEAN_PATH, ELAN_TOOLCHAIN을 잘못 설정해도 지정된 compiler와 의존성으로 재검증됐습니다.
  • 쓰기·네트워크 차단. 같은 파일 열기·접속 명령이 sandbox 밖에서는 성공하고 안에서는 실패했습니다.
  • 소스 도구 경로 제한. 상위 경로·절대 경로·외부 symlink 접근을 거절했습니다.
  • 일관성 대조. 실행 전후 artifact·pin, 입력·로그 해시, 제출 proof 해시를 확인했습니다.

추가 검증 필요

  • OS 수준의 파일 읽기 격리. 현재 compiler는 호스트 파일을 읽을 수 있습니다. 소스 도구의 경로 제한만으로 완전한 격리를 보장하지 않습니다.
  • Linux 이미지·깨끗한 재빌드. 기존 캐시의 bytes를 확인했으며 소스에서 다시 빌드하지 않았습니다.
  • 실제 agent·API 연결. 후보 생성, 자식 실행, 문제별 비용 제한은 이번 실험에 포함하지 않았습니다.
  • 공식 worker와의 동등성. 공식 서버에 제출하지 않았으며 같은 점수가 나오는지 확인하지 않았습니다.
  • 반복 측정과 전체 문제. 두 문제만 실행했고 heartbeat 계측은 proof·환경별 1회입니다.

PROPOSED INTERFACE · 추가 구현할 계약

tools = runner.bind(run_id)
context = tools.get_context()
source = tools.read_source(source_id="mathlib", relative_path="Mathlib/...")
feedback = tools.check(candidate_code)
receipt = tools.submit(candidate_code)

제한은 runner의 요청 처리와 OS 권한으로 적용합니다. Agent에게 별도 shell·파일 도구가 열려 있으면 이 인터페이스만으로 접근을 통제할 수 없습니다. submit()은 로컬 후보 등록이며 공식 사이트 업로드와 분리합니다.

03 / TEAM DASHBOARD

팀 대시보드 사용과 운영

문제별 점수와 실제 토큰·heartbeat를 함께 확인하고, 같은 실험 스냅샷 안에서 다음 개선 대상을 선택합니다.

화면 읽기점수와 색상기록과 단위로컬 실행데이터 갱신배포 설정
파일럿과 대시보드 기록의 연결. 앞 절의 10월 18일 환경 파일럿과 아래 10월 10일·16일 대시보드 스냅샷은 별도 실험입니다. 환경 파일럿을 대시보드에 연결하려면 스냅샷 입력 연결을 추가하고 문제 ID·후보 해시·환경·단위를 함께 보존해야 합니다. 문서 통합만으로 데이터가 자동 연동되지는 않습니다.

Lean Refactor Arena의 문제별 점수, 실제 토큰 길이와 heartbeat를 함께 확인하는 팀 대시보드입니다. 현재 공개된 15문제를 본대회 50문제 안에 포함하고, 나머지 35문제는 공개 대기로 표시합니다. 색상으로 개선 정도를 훑어보고, 숫자와 측정 근거로 다음 개선 대상을 선택합니다.

기준일은 2026년 10월 18일입니다. 구현 코드는 LeanAgent-LeanRefactorArena의 dashboard에 있으며, 팀원용 안내는 이 LeanAgent 저장소에서 관리합니다. 현재는 저장된 로컬 실험을 보여주는 정적 웹 앱이고, 팀 공유용 배포는 아직 완료되지 않았습니다.

화면 읽기

  1. 실험 기록에서 비교할 스냅샷을 선택합니다. 서로 다른 날짜의 결과를 한 화면의 측정값으로 섞지 않습니다.
  2. 전체 50 또는 현재 공개 15로 표시 범위를 정합니다. 현재 공개 수는 데이터의 공개 상태에 따라 늘어납니다.
  3. 개선 점수, 토큰, Heartbeat, 호환성, 대회식 종합 중 확인할 지표를 선택합니다. 검색, 출처 필터와 점수 정렬로 대상을 좁힐 수 있습니다.
  4. 문제 타일에서 선택한 지표의 점수와 후보의 토큰 길이 / HB를 확인합니다. 실제 두 수치는 지표 탭을 바꿔도 표시됩니다.
  5. 타일을 누르면 원본과 후보의 수치, 버전별 검증 결과, 측정 환경과 근거를 상세 패널에서 확인할 수 있습니다.

예를 들어 10월 16일 기록의 P01은 원본 313토큰에서 후보 43토큰으로 줄었고, raw heartbeat는 5,180,168에서 1,924,603으로 줄었습니다. 타일에는 개선 점수 74.55와 후보의 실제 두 수치를 함께 표시합니다. Heartbeat는 검증 작업량 지표이며 경과 시간이나 초 단위 수치가 아닙니다.

점수와 색상

점수 계산

지표계산의미
토큰(1 − 후보 토큰 / 원본 토큰) × 100증명 본문의 토큰 감소율
Heartbeat(1 − 후보 HB / 원본 HB) × 100같은 환경에서 측정한 heartbeat 감소율
개선 점수(토큰 감소율 + HB 감소율) / 2두 효율 지표를 같은 비중으로 합친 로컬 점수
호환성통과 버전 수 / 지정 버전 수 × 100동일 후보가 지정된 버전에서 통과한 비율
대회식 종합(토큰 감소율 + HB 감소율 + 호환성) / 3세 항목을 합친 로컬 추정 점수

이 수치는 공식 worker의 제출 결과와 구분합니다. 호환성은 지정된 버전의 검사가 모두 끝난 뒤 산출하며, 미검증 버전을 통과로 취급하지 않습니다. 원본 수치가 0이면 해당 감소율은 산출 대기로 표시합니다. 후보가 원본보다 커지면 감소율은 음수로 유지합니다.

상단 평균은 해당 지표가 산출된 문제만 사용하며 측정 문제 수를 함께 표시합니다. 검색이나 출처 필터를 바꿔도 상단 평균은 전체 스냅샷을 기준으로 유지합니다. 전체 50문제의 대회식 종합은 모든 문제 점수가 확정된 후 표시하고, 확정된 미제출·검증 실패는 0점으로 포함합니다.

초록색은 구간별 등급이 아니라 (점수 − 60) / 40의 비율로 보간합니다. 빨간색은 팀이 정한 개선 우선순위 표시이므로, 점수가 양수인 문제도 60 이하라면 경고색입니다. 증명 검증 실패 여부는 문제 상태와 상세 검증 결과에서 따로 확인합니다.

색상은 현재 탭에 표시된 점수를 따릅니다. 대회식 종합에서는 큰 숫자인 종합 점수가 색상을 결정하고, 화살표 옆의 p 값은 원본 종합 점수 대비 변화량을 나타냅니다.

두 기록 모두 50칸이며, P16–P50은 미공개 상태입니다. 현재 대시보드는 11월 1일 공개 예정이라는 팀의 전제를 반영합니다. 날짜가 지나도 문제나 측정값이 자동으로 생성되지는 않습니다.

원본과 후보는 같은 Lean 버전·소스 리비전·단위에서 비교합니다. raw와 scaled 값은 크기가 다르므로 절대값을 직접 비교하지 않습니다. 어떤 환경의 값인지 타일 위 안내와 문제 상세에서 확인합니다. 중앙값에 소수점이 있으면 반올림해 없애지 않고 보존합니다.

데이터 갱신

화면에서 JSON 미리 보기

JSON 내보내기로 현재 스냅샷을 저장하고, JSON 불러오기로 변경한 데이터를 확인할 수 있습니다. 불러온 파일은 브라우저 메모리에만 적용되므로 새로고침하면 기본 데이터로 돌아갑니다. 이 기능만으로 팀 공용 데이터가 갱신되지는 않습니다.

팀 공유 데이터의 갱신 순서는 다음과 같습니다.

  1. 새 JSON을 dashboard/public/data/에 추가하고 index.json 목록에 등록합니다. 기존 스냅샷을 갱신했다면 변경된 수치와 측정 근거를 확인합니다.
  2. 테스트·빌드와 브라우저에서 점수, 단위, 미측정 상태를 확인합니다.

Strata · PhysLib · CSLib · ArkLib · LeanPool · PutnamBench, 6개 출처에서 수집한 후보들의 길이·증명 방식·프로젝트 구성을 살펴봅니다. 원문 보고서 「최종 50문제 후보군에는 어떤 증명들이 있는가」의 통계와 해석을 함께 담았습니다.

후보군 통계와 실행 측정의 연결. 이 절은 수집한 증명의 구성에 관한 탐색적 분석입니다. 환경 파일럿이나 대시보드 스냅샷의 토큰·heartbeat 측정값과 합산하지 않습니다. 실제 실험에 사용할 후보를 고른 뒤에는 명제·문맥·소스 리비전으로 문제를 식별하고, 지정 환경에서 검증한 결과를 별도로 기록해야 합니다. 여기의 분석 대상은 공식 최종 50문제가 확정됐다는 뜻이 아닙니다.

최종 50문제 후보군을 이해하기 위한 분석

분석 전제: 6개 출처에서 가져온 자료를 최종 50문제의 후보군으로 본다. 후보들의 길이, 증명 방식, 출처와 하위 프로젝트의 특징을 파악하는 것이 목적이다.

수집한 추출 선언 382,121개 중, 직접 sorry/admit가 없는 by 증명 323,207개를 연결했다. PutnamBench 원본에는 이 조건을 만족하는 증명이 없어 아래 완성 증명 통계에서 빠진다. 이는 PutnamBench가 최종 문제의 출처 후보에서 빠진다는 뜻이 아니다. 완성된 Putnam warm-up 3개는 별도로 보관한다. 통계의 포함 조건과 최종 문제의 선정 조건을 구분한다.

1. 같은 풀이 표현이 서로 다른 후보에 쓰일 수 있다

서로 다른 명제도 by rfl, by simp 같은 동일한 코드로 증명할 수 있다. 본문 문자열 일치는 풀이 표현의 재사용으로 읽으며, 후보를 제거하는 기준으로 쓰지 않는다.

긴 후보 48,519개에 서로 다른 proof 문자열 48,048개가 나타난다. 문자열별 첫 출현 이후의 반복 출현 수는 471개 (0.97%)다. 명제와 증명이 함께 담긴 선언 원문 src가 그대로 반복되는 출현 수는 228개다.
