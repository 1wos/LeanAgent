## 한 줄 요약

LLM이 만든 Lean 증명은 옳아도 길다. 증명을 짧게 만드는 일과 컴파일 비용을 낮추는 일은 서로 충돌할 수 있다. 이 논문은 모델을 추가로 학습시키지 않고 **전략 검색 → 계획 → 수정 → Lean 검증 → 교정**을 반복하는 에이전트로 증명을 줄인다.

## 1. 논문을 읽기 위한 기본 개념

| 개념 | 뜻 | 내 담당 문제에서의 예 |
| --- | --- | --- |
| **증명 토큰** | 증명 본문을 구문 단위로 나눈 조각의 수. 이름 하나, 괄호 하나, 쉼표 하나가 각각 1개다. LLM의 토큰과 다르고, 주석과 빈 줄은 세지 않는다. 논문의 "증명 길이"가 이 값이다. | 참조 증명은 4번이 851, 9번이 251이다. |
| **heartbeat** | Lean이 선언 하나를 처리하면서 쓴 작업량의 계수. `#count_heartbeats`로 잰다. | 참조 증명의 공식 기준값은 4번이 11,947, 9번이 3,858이다. |
| **버전 호환성** | 같은 증명이 지정된 여러 Lean·Mathlib 버전에서 수정 없이 통과하는 비율. | 9번은 세 버전에서 채점된다. |
| **검증기(verifier)** | 후보 증명이 맞는지 판정하는 Lean 컴파일러. 채택은 모델의 자기 평가가 아니라 컴파일 결과로 정한다. | `lake env lean`으로 파일 전체를 컴파일한다. |
| **수정 전략** | "이런 형태의 증명은 이렇게 줄인다"는 재사용할 수 있는 처방. 논문은 긴 증명과 짧은 증명의 쌍 약 20만 개에서 뽑은 481,567건의 전략을 9,237개의 고유 전략으로 추려 전략 은행을 만들었다(3.1절). | 두 방향의 대칭 블록을 합친다. 여러 단계를 Mathlib 정리로 바꾼다. |
| **고정된 LLM** | 추가 학습 없이 그대로 쓰는 LLM. 논문 실험의 기본 모델은 Gemini 3 Flash다. | - |

## 2. 반복 구조 (3.3절, Algorithm 1)

논문은 증명에 그 증명이 호출하는 의존 항목의 시그니처를 붙인 뒤, 아래 네 단계를 반복한다.

1. **검색**: 증명을 여러 크기의 구간으로 나누고 구간마다 전략 은행에서 상위 K개의 전략을 가져온다. K는 검색 개수를 정하는 설정값이다.
2. **계획**: 현재 증명, 검색된 전략, 실행 이력을 보고 구간별 수정 단계의 목록을 만든다.
3. **수정**: 계획의 한 단계를 받아 해당 구간 또는 증명 전체를 다시 쓴다. 만든 후보를 Lean 컴파일러에 넘긴다.
4. **교정**: 컴파일에 실패하면 컴파일러의 오류 메시지를 LLM에 돌려보내 고치게 한다. 계획의 원래 의도 안에서만 고친다.

| 항목 | 논문의 규칙 | 실험 설정 (부록 I.4) |
| --- | --- | --- |
| 채택 기준 | 컴파일에 성공하고 증명 토큰이 줄어야 한다. 둘 중 하나라도 아니면 채택하지 않는다. | - |
| 실패 처리 | 교정 횟수 안에 통과하지 못하면 그 단계를 기록하고 건너뛴다. | 교정 최대 3회 |
| 재계획 | 채택되면 갱신된 증명과 이력으로 계획을 다시 세운다. | - |
| 종료 | LLM 호출 수가 예산에 도달하거나 증명 토큰이 목표 아래로 내려가면 끝낸다. | 호출 예산 30회, 목표 5토큰 |

논문에서 이 구조를 찾아 읽으려면 3.3절과 Algorithm 1을 보면 된다. Figure 4는 전략 은행 구축과 검색까지 포함한 전체 개요다. Algorithm 1의 주석은 교정 부분을 "Verifier-guided self-debugging loop"라고 부른다.

## 3. Lean이 돌려주는 것과 그 사용 방식

Lean 컴파일러가 돌려주는 것은 성공 여부와 오류 메시지다. 이 두 가지가 루프의 갈림길을 정한다.

- **성공**: 증명 토큰이 줄었으면 후보를 현재 증명으로 채택하고 계획을 다시 세운다.
- **실패**: 오류 메시지가 교정 단계의 입력이 된다. 교정 프롬프트(부록 O)는 오류를 먼저 분석할 것, 이미 얻은 단축을 유지할 것, 원래의 긴 증명으로 되돌아가지 말 것을 지시한다.

목표가 달라지면 검색 규칙이 달라진다(3.2절). 길이가 목표이면 증명 구간과 가장 비슷한 전략을 그대로 쓴다. 컴파일 시간이 목표이면 전략에 주석된 절감량 순으로 재정렬한다. 특정 버전이 목표이면 그 버전에서 통과한 전략만 남긴다.

논문 본문의 채택 기준은 세 경우 모두 컴파일 성공과 길이 감소다. 저자의 공개 코드는 여기에 더해 길이와 heartbeat의 가중합이 좋아질 때 채택하는 `--multi-objective` 옵션을 제공한다.

## 4. 무엇을 개선으로 보는가 (4절)

지표는 증명 길이, 컴파일 비용, 버전 호환성 세 가지다. 컴파일 비용은 경시 수학 문제에서는 컴파일 시간으로, 연구용 Lean 프로젝트에서는 heartbeat로 잰다. 실험의 기본 설정은 Gemini 3 Flash, Lean `v4.24.0`, 호출 예산 30회다.

아래 표의 miniF2F와 PutnamBench는 경시 수학 문제 모음이고 PhysLean은 물리 형식화 프로젝트다. "상대 감소"는 문제별 감소율의 평균이다. 음수이면 평균적으로 늘었다는 뜻이다.

## 5. 작은 예제: 담당 문제에 적용한 기록

논문의 반복 구조 가운데 수정, Lean 검증, 교정, 채택 단계를 담당 문제에 적용했다. 전략 은행 검색은 적용하지 않았다. 아래는 [4·9번 리팩터링 기록](../../meetings/2026-10-11-week2/refactoring-04-09.md)에 있는 9번의 시도 3과 시도 4다. 환경은 Lean `v4.32.0`, cslib 커밋 `197a7be`, Mathlib 커밋 `81a5d25`다.

**수정 (시도 3)**: 경우 분석을 `rintro` 패턴 한 줄로 썼다.

```lean
    · rintro s (t | t)
      · obtain ⟨s', a, b⟩ := h.follow_fst t
        exact ⟨s', Tr.choiceL a, ChoiceBisim.bisim b⟩
      · exact ⟨s, Tr.choiceR t, ChoiceBisim.bisim (HomBisimilarity.refl _)⟩
```

**Lean 결과**: 실패했다. 오류 메시지는 `Unknown identifier 't'`였다.

**교정 (시도 4)**: 오류의 원인을 찾았다. 전이 관계 `Tr`의 생성자는 8개이고 `choiceL`과 `choiceR`는 다섯째와 여섯째다. 생성자 두 개짜리 패턴 `(t | t)`는 앞쪽 생성자에 대응되어 실제 경우에서는 `t`라는 이름이 붙지 않았다. 같은 시도에서 이미 줄여 둔 다른 부분은 그대로 두고 이 부분만 고쳤다.

```lean
    · intro s t
      cases t
      next t =>
        obtain ⟨s', a, b⟩ := h.follow_fst t
        exact ⟨s', Tr.choiceL a, ChoiceBisim.bisim b⟩
      next t => exact ⟨s, Tr.choiceR t, ChoiceBisim.bisim (HomBisimilarity.refl _)⟩
```

**Lean 결과와 채택**: 통과했다. 증명 토큰은 198 → 169, heartbeat는 441 → 380이 되어 채택했다.

논문의 방식과 이번 기록의 방식은 다음과 같이 다르다.

| 단계 | 논문 | 이번 기록 |
| --- | --- | --- |
| 전략 검색 | 전략 은행에서 검색한다. | 하지 않았다. 수정 후보는 참조 증명을 읽고 정했고, 4번에서는 Mathlib에서 같은 종류의 정리를 찾았다. |
| 채택 기준 | 컴파일 성공과 길이 감소 | 컴파일 성공과, 토큰 감소율과 heartbeat 감소율의 평균 증가 |
| 교정 한도 | 3회 | 3회 |
| 종료 | 호출 예산 30회 또는 목표 길이 | 검증 실행 횟수 한도(시도 묶음마다 14회) |
| 버전 검증 | 한 환경 | 최종 후보를 지정 환경 전부에서 확인 |
| 비용 집계 | LLM 호출 횟수 | 하지 않았다. |

채택 기준의 차이가 결과를 바꾼 사례가 있다. 9번의 시도 1은 `v4.32.0`에서 증명 토큰이 251 → 262로 늘고 heartbeat가 3,856 → 497로 줄었다. 논문의 기준으로는 기각되지만 길이와 heartbeat를 함께 보는 대회 채점식으로는 큰 이득이다.

## 6. 우리 프로젝트에 적용할 점

이번 기록에서는 다음을 이미 적용했다.

- **검증 명령을 하나로 고정했다.** 명제 보존, 금지 패턴, 컴파일과 공리, 토큰, heartbeat를 한 번에 확인하는 [검증 스크립트](../../meetings/2026-10-11-week2/refactoring-04-09/verify_candidate.py)를 두었다. 후보를 재기 전에 참조 증명에서 공식 기준값이 나오는지 먼저 확인했다.
- **채택 기준을 대회 채점식에 가깝게 잡았다.** 지정 환경 통과를 전제로 두고 토큰 감소율과 heartbeat 감소율의 평균으로 후보를 비교했다.
- **교정에 한도를 두었다.** 수정 하나에 교정 3회를 넘기면 건너뛰고 기록한다. 교정할 때는 이미 얻은 단축을 유지한다.
- **시도 기록의 단위를 루프에 맞췄다.** 시도마다 바꾼 내용, Lean 결과와 오류 원문, 토큰, heartbeat, 채택 여부를 남겼다.

하네스를 만들 때는 다음이 새로 필요하다.

- **검색 단계**: 전략 은행과 검색 모델은 공개 저장소에 들어 있지 않다. 이번 기록에서 가장 큰 절감은 4번에서 Mathlib의 정리를 찾은 데서 나왔으므로 수정 전에 라이브러리를 검색하는 단계를 두는 방안이 유력하다.
- **버전별 검증의 자동화**: 이번에는 저장소 사본 세 개를 손으로 준비해서 확인했다. 공개 코드는 작업 공간 하나에서만 컴파일한다. 대회에서는 지정 환경 통과율이 문제 점수의 3분의 1이다.
- **비용 집계**: 공개 코드는 예산을 호출 횟수(30회)로 센다. 대회는 문제당 US$3의 비용 기록을 요구한다.

## 7. 한계와 읽지 않은 부분

- 논문은 버전 호환성 실험을 경시 수학 문제로 제한했다. 연구용 프로젝트는 특정 Lean 버전에 고정되어 있어서 버전을 바꾸면 수정의 품질과 무관하게 컴파일이 깨지기 때문이다(4.3절, 6절).
- 전략에 주석된 버전은 `v4.14.0`, `v4.16.0`, `v4.22.0`, `v4.24.0`이다(3.1절). 웜업 문제의 `v4.31.0`–`v4.33.0-rc2`는 이 범위 밖이다.
- 논문의 PhysLean은 웜업 4번의 출처인 PhysLib과 같은 저장소다. GitHub가 `HEPLean/PhysLean`을 `leanprover-community/physlib`으로 연결한다.
- 부록 A, E, G와 부록 B의 대부분(B.5 제외)은 읽지 않았다. 그림은 캡션과 본문의 설명만 확인했다.
- 같은 분야의 시작 자료로 지정된 APOLLO(arXiv:2505.05758)와 Learning to Repair Lean Proofs from Compiler Feedback(arXiv:2602.02990)은 초록만 확인했다. 앞의 논문은 실패한 부분 증명을 분리하여 다시 증명하고 재결합하는 반복을 다룬다. 뒤의 논문은 틀린 증명과 컴파일러 피드백에서 고친 증명을 예측하도록 학습하는 데이터셋 APRIL을 다룬다.
