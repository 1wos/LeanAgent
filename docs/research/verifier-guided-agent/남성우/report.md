# 검증·수리·선택 파이프라인: 이번 주 구현과 실험

남성우 · 공유일 2026-10-18 · 작업 범위 2026-10-12–17.

대표 [HTML 발표](presentation.html)는 비전공 독자도 흐름을 따라갈 수 있도록 목적, 계약, 파이프라인, 실제 사례, 결과, 남은 과제 순서로 구성했다. 이 문서는 코드와 결과를 찾기 위한 상세 안내다.

## 이번 주의 결론

Lean으로 증명이 맞는지 확인한 다음에도 제출 후보 선택이 필요하다. 수리에 성공한 proof가 더 많은 토큰이나 heartbeat를 사용한다면 원본보다 나쁜 제출물이 될 수 있다. 따라서 **검증 → 로컬 수리·최적화 → 재검증·계측 → 최고 점수 선택**을 분리하고, 더 나은 후보를 찾지 못하면 검증된 원본을 사용한다.

15문제에 세 범용 프롬프트를 적용한 45개 슬롯을 기록했다. 실제 변경 body는 40개다. 8번 세 슬롯은 사용자 지정 원본 보존이며, 6·7번 P2도 원본 그대로다. 지정 버전 조합 36개에서 원본과 선택 proof를 검증했다. 최종 선택은 14문제 개선, 8번 원본 보존이다. 원본의 로컬 점수 33.3333에 대해 선택 점수 평균은 35.2683이다.

최초 후보는 개선 30개, 유효하지만 악화 3개, invalid 7개, 원본 유지 5개였다. Escalation 프롬프트는 12개를 출력했고 실제 모델 escalation은 수행하지 않았다. [전체 결과](evidence/warmup-2026-10-15/REPORT.md)와 [측정 요약](metrics.json)을 함께 확인한다.

## 변경하지 않는 것

명제, binder, 가정, 답을 나타내는 정의, import, option, 주변 선언은 고정한다. 원본 파일의 선언을 정확히 찾아 body 범위를 정하고, 출력 파일이 `원본 prefix + 후보 body + 원본 suffix`인지 비교한다. 새 sorry·공리와 문맥 변경을 허용하지 않으며 전체 파일 검사 후 대상 정리의 공리 의존성을 원본과 비교한다.

현재 body 내부 명령 삽입 검사는 단순 거부 검사다. 일반적인 악성 입력을 방어하는 Lean AST firewall은 아직 아니다. 기존 정책은 목표 정리 자기참조를 금지한다. 정상 재귀 원본인 8번은 정책을 임의로 완화하지 않고 원본만 보존했다.

## LLM 없이 실행하는 연산

유효한 후보에서는 단독 `simp`, `simp_all`, `aesop`의 앞 두 위치까지 `?`로 질의한다. 한 줄로 명확히 추출되는 제안을 새 body에 넣고 전체 파일과 모든 지정 버전에서 같은 body를 검증한다. 로컬 탐색용 `?` proof 자체는 제출 pool에 넣지 않는다. 다중 줄 제안 추출과 여러 위치를 조합하는 탐색은 후속 과제다.

invalid 후보에서는 첫 진단 줄이 단순한 본문 줄이면 그 줄을, 그렇지 않으면 본문 전체를 대상으로 `assumption → rfl → omega → simp? → exact? → aesop?`를 시도한다. 첫 유효 결과에서 중단하며, 제안 추출 후 다시 검증한다. 이것은 제한된 텍스트 위치 추정이지 신뢰 가능한 tactic-state localization은 아니다.

[실행기](evidence/warmup-2026-10-15/run_sweep.py)는 검증·계측·고정 연산을 담당하고, [정책 코드](evidence/warmup-2026-10-15/escalation_policy.py)는 관찰 JSON으로부터 행동과 선택적 프롬프트를 만든다. 정책 코드 자체가 Lean이나 모델 API를 실행하지 않는다.

## Escalation의 결정 조건

| 관찰 | 처리 |
| --- | --- |
| 환경 오류 | 환경 복구. proof invalid로 확정하지 않음 |
| 원본 미검증 | fallback으로 쓰기 전에 원본부터 검증 |
| 계약 불일치 | 후보 거부 |
| 고정 로컬 연산이 남음 | 로컬 시도 먼저 실행 |
| 로컬 수리 후 invalid | 수리 요청 검토 |
| 유효하지만 계측·버전 확인 미완료 | 계측을 끝내기 전 최적화 판단 보류 |
| 후보 점수 ≤ incumbent, HB ≥ 원본의 125%, 또는 관찰된 버전 실패 | 최적화 요청 검토 |

125%는 지출 결정을 위한 휴리스틱이며 개선 가능한 증명의 존재를 증명하지 않는다. 숫자는 현재 정책의 설정이며 보편적인 최적 임계값으로 검증된 것이 아니다.

좁은 scope의 상태 인증은 candidate/environment hash, 실패 tactic 이전 capture, prefix replay 성공, 오류·recovery·sorry 없음, 재현 state digest 일치를 요구한다. 이번 실행기는 이 인증을 제공하지 않아 모델에 보낼 요청은 body 범위로 출력했다. 코드의 기본 한도는 repair 2회·optimization 1회이며 실제 호출 때 비용 상한을 검사한다. 이 반복 호출 루프는 이번 실험에서 실행하지 않았다. `preview_only`는 프롬프트 확인용이며 호출 승인이나 예산 승인을 의미하지 않는다.

프롬프트에는 명제·문맥·원본·후보·진단·시도 이력·측정값·제약을 포함한다. 반환 형식은 `candidate`, `need_context`, `no_candidate` 중 하나와 complete proof body다. [실제 요청 목록](evidence/warmup-2026-10-15/REPORT.md)에서 12개 파일을 열 수 있다.

## 실제로 관찰한 두 사례

### 13번 P2: 길이 증가보다 HB 감소가 컸다

`simp_all`을 `simp_all only [ge_iff_le, ne_eq]`로 추출했다. P2 최초 후보 2,595토큰·119,536.024 HB·40.0603점에서 추출 후보 2,605토큰·114,038.769 HB·41.2370점으로 개선됐다. 같은 body가 4.25·4.26·4.27을 통과했다. 10토큰이 늘어도 비용 감소가 더 커서 선택됐다.

### 9번 P1: 수리 성공 후 원본 fallback

오류가 난 `exact .choice _ _ _ h`를 `exact?` 탐색에서 얻은 `exact ChoiceBisim.choice h`로 바꿨다. 명시적 proof는 세 버전을 통과했지만 33.0497점으로 원본 33.3333보다 낮아 채택하지 않았다. P1 분기는 최적화 프롬프트를 출력하고 원본 fallback으로 끝났다. 문제 전체에서는 별도 P2 후보의 43.5486점을 선택했다.

탐색용 `exact?` proof는 일반 검증과 동기 계측에서 서로 다른 결과를 보였다. 명시적으로 추출한 proof는 두 검사 모두 통과했다. 탐색 성공을 최종 제출 성공으로 곧바로 취급하지 않는 이유다.

## 점수와 해석 범위

`S = (100*(1-L/L0) + 100*(1-H/H0) + 100*passed/total)/3`.

토큰은 tiktoken 0.14.0 / o200k_base로 원본·후보 proof body 전체를 다시 센다. HB는 동기 elaboration에서 `IO.getNumHeartbeats` 차이를 1,000으로 나눈 값이다. 첫 지정 버전을 길이·HB 기준으로 사용하고, robustness는 모든 지정 버전에서 같은 body의 통과 비율이다. 단순 wall time을 HB로 대체하지 않았다.

공식 worker와 동등함을 확인하지 않은 **로컬 모의 점수**다. 13번 원본은 공개 HB 111,476과 로컬 HB 141,079.649가 다르다. 공개 길이와 로컬 토큰 분모를 섞지 않았고 [비교 표](evidence/warmup-2026-10-15/REPORT.md)에 각각 기록했다.

같은 대화 문맥에서 1회 후보를 만들었으며 1·2번은 사전 노출이 있다. 독립 표본이나 일반 성능 순위가 아니다. 일부 개선폭은 작다. 이 결과만으로 프롬프트의 일반 우열이나 공식 점수 개선을 주장하지 않는다.

## 도구 검토에서 실제로 채택한 범위

이번 주 문헌 검토에서는 [LeanFlow](https://arxiv.org/abs/2607.20503)의 상태·실패 이력 보존과 statement/proof 역할 구분, [Lean Copilot](https://arxiv.org/abs/2404.12534)의 tactic 후보를 실행 결과로 구분하는 인터페이스를 참고했다. Arena에는 명제가 이미 주어지므로 statement 번역·모델 reviewer를 MVP에 추가하지 않았다.

현재는 Python과 Lean CLI를 사용한다. LeanFlow·Lean Copilot 패키지를 설치·통합해 얻은 결과가 아니며 논문 성능 수치를 Arena 기대 성능으로 사용하지 않았다. [LeanProbe](https://github.com/epfl-lara/LeanProbe)/LeanInteract 연결과 warm 환경 재사용은 버전·문맥 호환성 검사를 거칠 후속 선택지다.

## 검증기 수리와 재현

`module` 파일의 공리 출력 제한은 별도 import probe로 처리했다. 계측 import를 module 뒤에 넣었고, wrapper가 후속 `omit`에 영향을 준 경우에는 전체 파일을 먼저 원래대로 검증한 뒤 별도 계측 사본만 대상 선언 직후 종료했다. 검사기 오류를 후보 실패로 집계하지 않았다. ArkLib 10번 구버전의 정확한 공백 한 개 차이만 원문 diff 확인 후 매핑했다.

[재현 README](evidence/warmup-2026-10-15/README.md)에 환경·명령·한계를 기록했다. [audit.json](evidence/warmup-2026-10-15/audit.json)의 누락 목록은 비어 있고 고정 입력 해시와 선택 proof의 검증 근거를 검사했다. 이전 실험의 source·측정 JSON·원시 로그는 내용 변경 없이 `evidence/` 아래에 보관했다. 기록 속 절대 실행 경로는 당시 provenance이며 실행 위치는 README 안내를 따른다.

다음 단계는 AST 보호, 실패 직전 상태 인증, 다중 줄 제안 추출, 공식 계측과의 비교, 예산을 관리하는 실제 모델 반복 루프다. 이번 결과는 그 전체를 검증한 것이 아니라 먼저 구현한 검증·로컬 처리·선택·프롬프트 출력 경로를 검증한 것이다.
