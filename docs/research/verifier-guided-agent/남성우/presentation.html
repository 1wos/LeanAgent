01 · 해결하려는 문제

맞는 증명과 좋은 제출물은 다르다

검증 질문

이 증명이 주어진 명제를 증명하는가?

Lean으로 전체 파일을 검사하고, 대상 정리에 새 공리 의존성이 생기지 않았는지 확인합니다.

선택 질문

원본보다 높은 점수를 얻는가?

proof 토큰 수, elaboration heartbeat, 지정 버전 통과율을 함께 비교합니다.

수리 성공 ≠ 점수 개선 ≠ 최종 채택

예를 들어 자동화 tactic이 오류를 해결해도, 탐색 때문에 heartbeat가 늘면 원본보다 낮은 점수를 받을 수 있습니다. 그래서 검증기와 선택기를 분리했습니다.

Heartbeat Lean 내부 연산량을 나타내는 계수. 초 단위 실행 시간과 다릅니다.

Robustness 동일한 proof body가 지정된 여러 Lean·라이브러리 버전에서 통과하는 비율.

Fallback 더 나은 후보를 확보하지 못했을 때 제출하는, 미리 검증한 원본 증명.

02 · 리팩터링 계약

바꿀 수 있는 것은 증명의 본문뿐

고정: import · 정의 · namespace · theorem statement
교체 가능: proof body
고정: 뒤쪽 선언 · 주변 문맥

명제, 가정, binder, 답을 나타내는 정의, import, option을 바꿔 문제를 쉽게 만들지 않습니다. 새로운 sorry나 공리로 통과시키는 것도 허용하지 않습니다.

현재 구현에서 한 일

  • 고정 benchmark 선언을 원본 파일에서 정확히 찾아 proof 범위를 계산했습니다.
  • 후보를 넣은 파일이 원본 prefix + 후보 body + 원본 suffix와 일치하는지 비교했습니다.
  • 전체 파일 검증 후 #print axioms로 원본·후보의 대상 정리 의존성을 비교했습니다.
보호 범위의 한계: body 안의 명령 삽입은 간단한 거부 검사로 확인합니다. 임의의 악성 입력까지 막는 일반적인 Lean AST 검증기는 아직 구현하지 않았습니다.

04 · 고정 로컬 연산

LLM 없이도 새 후보를 만들 수 있다

올바른 후보를 더 명시적으로 만들기

탐색 전
simp_all
탐색용 사본
simp_all?
제안을 추출한 새 후보
simp_all only [ge_iff_le, ne_eq]

13번에서 실제로 얻은 변환입니다. 사용할 규칙을 Lean에 물어보고, 제안을 본문에 넣은 뒤 전체 증명을 다시 검사합니다. 모델에게 다시 작성해 달라고 요청하지 않았습니다.

현재 구현의 탐색 범위

  • 정상 후보: 단독 simp / simp_all / aesop 중 앞의 두 위치까지 탐색합니다.
  • 한 줄로 추출할 수 있는 제안만 받아들입니다. 다중 줄 스크립트 추출은 미구현입니다.
  • 로컬 ? 탐색 proof 자체는 제출 pool에서 제외하고 명시적 추출 결과를 평가합니다.
  • 추출이 성공해도 점수 개선을 보장하지 않습니다. 원후보와 추출 후보를 모두 비교합니다.
05 · 수리와 위치 추정

오류가 난 줄이 원인의 전부일까?

Lean 진단의 줄 번호는 유용한 출발점입니다.
하지만 실패 직전의 신뢰 가능한 goal을 자동으로 보증하지는 않습니다.

이번에 구현한 로컬 수리

첫 오류 줄이 body 내부에 있고 후속 들여쓰기 블록이나 case header가 아니면 한 줄 교체를 시도합니다. 아니면 본문 전체 solver를 시도합니다.

assumption → rfl → omega
→ simp? → exact? → aesop?

각 시도는 전체 파일을 재실행하며, 첫 유효 결과에서 탐색을 멈춥니다.

보수적으로 넘긴 LLM 문맥

이번 실행기에는 실패 직전 tactic state의 재현 인증이 없습니다. 따라서 LLM 프롬프트는 body 범위로 내보냈습니다.

명제·문맥·원본·후보·첫 오류와 후속 진단·실패한 시도·측정값을 함께 제공합니다.

도입부의 잘못된 intro, 잘못 고른 귀납 가정, 앞선 have도 뒤쪽 오류의 원인이 될 수 있습니다. “오류 줄만 고치면 된다”를 전제로 삼지 않습니다.
06 · Escalation 정책

애매한 판단 대신 기록 가능한 조건으로

관찰다음 행동
환경 오류 / 원본 미검증환경 복구 / 원본 검증. 후보 실패로 처리하지 않음
본문 밖 변경 또는 계약 불일치후보 거부
로컬 시도가 남음먼저 고정 로컬 연산 실행
로컬 수리 후에도 invalid수리 프롬프트 출력
유효하지만 계측·버전 확인 미완료계측 완료 전 최적화 판단 보류
점수 ≤ incumbent, 또는 HB ≥ 원본의 125%, 또는 관찰된 버전 실패최적화 요청 검토

125%는 정책상의 휴리스틱입니다. 개선 가능한 증명이 존재한다는 수학적 판정이 아닙니다. tactic 이름만으로 “비싸다”고 판단하지 않습니다.

실제 호출 루프를 연결할 때의 정책

기본 한도는 repair 2회, optimization 1회입니다. 비용 상한과 사용·예약 금액을 확인하고 동일 실패가 반복되면 편집 범위를 넓힙니다. 이 정책 분기는 코드에 있지만, 이번 실험에서는 실제 모델 반복 호출을 실행하지 않았습니다.

좁은 범위의 상태 인증은 candidate/environment hash 일치, 실패 tactic 이전 capture, prefix 재실행 성공, 오류·recovery·sorry 없음, state digest 일치를 요구합니다. 이번 실행기는 이 인증을 발행하지 않습니다.

07 · 실험 설계

실패를 만들지 않고 실제 후보를 흘려보냈다

P1

구조 유지·간소화

기존 논리와 분기를 유지하며 중복 단계, 불필요한 have, tactic 연결을 줄입니다.

P2

구조 개선

반복되는 논증, 더 적절한 귀납, 기존 lemma로 긴 유도를 대체할 가능성을 찾습니다.

P3

비용 축소

직접 lemma 적용, 좁은 simp 규칙, 반복 정규화 축소를 시도합니다.

  • 15문제 × 3개 프롬프트 = 45개 슬롯. 8번 3개는 원본 보존, 6·7번 P2도 원본 유지: 실제 변경 body는 40개입니다.
  • 같은 대화 모델이 후보를 작성하고, 검증 피드백 전에 고정했습니다. 실패를 인위적으로 삽입하지 않았습니다.
  • 이후 모델의 재수정 없이 고정 로컬 연산과 정책을 실행했습니다.
  • 8번의 정상 재귀는 기존 자기참조 금지 정책과 별도 검토가 필요해, 사용자 결정으로 원본만 보존했습니다.
독립 세션·반복 샘플로 통제한 실험이 아닙니다. 특히 1·2번은 이전 대화에서 사전 검토했습니다. 프롬프트의 일반적인 우열로 확대 해석하지 않습니다.
08 · 로컬 모의 점수

무엇을 어떻게 점수로 비교했나

S = ⅓ × {100(1 − L/L₀) + 100(1 − H/H₀) + 100·p/v}

L / L₀ 후보 / 원본 proof body의 o200k_base 토큰 수

H / H₀ 후보 / 원본 정리의 동기 elaboration heartbeat

p / v 동일 후보가 통과한 버전 수 / 지정 버전 수

모든 버전을 통과한 원본은 33.3333입니다. 후보가 원본보다 엄격하게 높은 점수를 얻어야 채택합니다. 길이·HB 기준은 목록의 첫 지정 버전입니다.

  • heartbeat는 IO.getNumHeartbeats 차이를 1,000으로 나눴습니다.
  • 계측용 코드는 별도 사본에만 들어갑니다. 제출 body에는 포함하지 않습니다.
  • 공개 proof_length를 로컬 토큰 분모와 섞지 않았습니다. 공식 기준값과 로컬 값은 별도 표로 보존했습니다.
공식 평가 worker와 동등한 계측기임을 입증하지 않았습니다. 예를 들어 13번 원본은 공개 HB 111,476, 로컬 HB 141,079.649로 차이가 납니다. 이 발표의 점수는 로컬 실험 안에서만 비교합니다.

10 · 실제 사례 — 9번 P1

고쳤지만, 채택하지 않은 증명

오류가 난 후보의 한 줄
exact .choice _ _ _ h
exact? 제안 추출 결과
exact ChoiceBisim.choice h

고정 로컬 solver 목록에서 exact?가 제안을 찾았습니다. 명시적인 코드로 추출한 body는 세 버전에서 검증됐지만, 점수는 원본보다 낮았습니다.

33.3333원본 점수
33.0497수리된 P1 점수
43.5486별도 P2 후보 점수

P1 분기는 최적화 요청 프롬프트를 남기고 원본 fallback으로 끝냈습니다. 문제 전체의 최종 선택은 더 좋은 P2 후보입니다.

exact? 탐색 proof는 일반 검증에서는 통과했지만 동기 계측 문맥에서는 실패했습니다. 반면 추출한 명시적 proof는 양쪽에서 통과했습니다. 그래서 탐색 코드 자체와 최종 제출 후보를 분리합니다.
