# 담당 5·10번: 증명 리팩터링 기록

작성: 박성호 · 검증일: 2026-10-11 · 공유: 2026-10-11 W02 모임

두 문제 모두 명제(`statement`)를 그대로 두고 증명만 바꿔, 원본보다 짧고 가벼운 검증 통과본을 만들었다. 최종본은 사람 개입 없이 원본에서 출발한 자동 파이프라인의 결과이고, API 비용은 문제당 $3 안이다.

| 문제 | 증명 토큰: 원본 → 최종 | heartbeat: 원본 → 최종 | 버전 호환 | 대회 방식 점수 | API 비용 |
| --- | ---: | ---: | --- | ---: | ---: |
| 5 | 1,372 → **721 (−47.4%)** | 26,817 → **11,188 (−58.3%)** | 1/1 · 100% | 68.6 | $2.58 |
| 10 | 1,463 → **484 (−66.9%)** | 15,902 → **8,802 (−44.6%)** | 4/4 · 100% | 70.5 | $2.53 |

대회 방식 점수 = (토큰 감소율 + heartbeat 감소율 + 버전 호환율) / 3. heartbeat는 지정 버전 중 최신(5번 v4.32.0, 10번 v4.31.0) 기준이다. 최종 증명은 사람이 손대지 않은 파이프라인 출력 그대로다. 최종 증명: [P05.lean](2026-10-11-박성호-warmup-05-10/P05.lean) · [P10.lean](2026-10-11-박성호-warmup-05-10/P10.lean). 측정값: [metrics.json](2026-10-11-박성호-warmup-05-10/metrics.json).

### 10번 버전별 결과

10번은 지정 버전이 4개다. 버전마다 해당 커밋의 ArkLib을 빌드하고, 그 버전 파일 안에서 선언을 교체해 검사했다. 옛 버전 파일은 명제는 같고 증명 안의 공백만 다르다. 기록: [P10_versions.jsonl](2026-10-11-박성호-warmup-05-10/compat/P10_versions.jsonl)

| --- | --- | ---: | ---: | ---: | --- |
| v4.31.0 | `c1712f6` | 15,897 | 8,802 | 44.6% | 통과 / 통과 |
| v4.30.0 | `e6d77b1` | 17,331 | 10,294 | 40.6% | 통과 / 통과 |

최종본은 `mul_le_mul_left'`를 쓰는데, v4.31.0에서 deprecated 경고가 나지만 4개 버전 모두 컴파일된다. 경고가 알려 준 새 이름 `_root_.mul_le_mul_right`로 바꾼 판도 4개 모두 통과했지만, 사람이 손댄 결과가 되므로 최종본으로 쓰지 않았다.

## 2. 측정 방법

- **토큰:** 주최 측 저장소 [`lean-refactor`](https://github.com/delta-lab-ai/lean-refactor)의 `proof_length()`. Warm-up 15문제 원본 중 14문제에서 공식 `proof_length`와 정확히 같다.
- **heartbeat:** 원래 파일 안에서 대상 선언만 바꿔 끼우고 `set_option Elab.async false` + `#count_heartbeats in`으로 쟀다. 독립 프로세스 3회 모두 같은 값이 나왔다.
- **통과 판정:** 명제 원문 일치, 원본과 수정본의 `#check`·`#print axioms` 출력 동일(`[propext, Classical.choice, Quot.sound]`, `sorryAx` 없음), 대상 정리에 `warningAsError`를 걸어도 진단 0. 5번은 파일 전체 `-DwarningAsError=true`에서도 오류 0이다. 10번 최종본은 대상 정리에 deprecated 경고 1개가 있다(컴파일에는 영향 없음). 10번 파일은 대상과 무관한 다른 선언에 원래부터 `sorry`와 deprecated 경고가 있어 파일 전체 엄격 모드는 원본부터 실패한다.

## 3. 어떻게 줄였나: 자동 파이프라인

```text
원본 → [주최 측 cc_agent 1라운드: sonnet, 상한 $1.50]
     → [결정적 후처리: LLM 없음]
     → [cc_agent 2라운드: opus, 남은 예산]
     → [결정적 후처리] → 최종
```

- **cc_agent**는 주최 측 베이스라인이다. 정리마다 Claude Code 세션을 띄우고, lean-lsp로 컴파일을 확인하며 증명을 줄인다. 점수 가중치는 길이 0.5, heartbeat 0.5로 두었다.
- **후처리**는 오늘 손으로 해 보며 찾은 규칙이다. 쓰이지 않는 `simp` 인자와 아무 일도 안 하는 tactic 제거, `simp?` 제안으로 `simp only [...]` 고정, `field_simp` → `ring`, `simp only at *` 삭제, `by exact t` → `t`. 변경마다 Lean으로 다시 판정하고 점수가 내려갈 때만 채택한다.
- 규칙의 근거는 [openai/math](https://github.com/openai/math)의 Lean 코드 2만 파일 집계다. `have`·`exact`·`rw`가 tactic의 71%이고 `simp`는 5%로, 자동 탐색 대신 정확히 지정하는 스타일이다(9절 참고).

## 4. 문제별 핵심 변화

**5번 (125줄 → 60줄).** 12단계 `calc`가 3단계가 됐다. 미분 계산을 단계마다 식으로 다시 적지 않고, `rw`와 `simp only [...]` 한 묶음으로 이어서 처리한다. 이름 없는 `simp`를 모두 `simp only`로 고정한 것이 heartbeat 감소의 대부분이다. 미분 가능성 부수 조건의 `by simp`는 `by decide`로 바뀌었다.

**10번 (208줄 → 37줄).** 지역 정의 5개와 보조 사실 여러 개를 없앴다. 섬유 합집합의 크기를 직접 세던 긴 블록을 Mathlib의 `Finset.card_biUnion_le_card_mul` 한 번으로 바꿨다. 마지막 산술은 `simp only [...] at h3`와 `omega`로 닫는다.

## 5. 실험 비교

아래 점수는 파이프라인이 내부에서 쓰는 점수 = 0.5 × 토큰 비율 + 0.5 × heartbeat 비율이다(원본 = 1, 낮을수록 좋음). 에이전트 설정마다 1회 실행이라 차이가 우연일 수 있다.

| 방법 | 5번 | 10번 |
| --- | ---: | ---: |
| 손으로 정리 + openai/math 규칙(대화형) | 0.725 | 0.889 |
| cc_agent, 원래 프롬프트 | 0.849 | 0.686 |
| cc_agent, 규칙을 프롬프트에 추가 | 0.910 | 0.758 |
| cc_agent 결과 + 규칙 후처리 | 0.697 | 0.653 |
| **자동 파이프라인(최종)** | **0.471** | **0.443** |

## 6. 인사이트

1. **규칙은 프롬프트보다 후처리로 붙이는 편이 나았다.** 같은 규칙을 프롬프트에 넣으면 두 문제 모두 나빠졌고, 에이전트 결과 뒤에 기계적으로 적용하면 좋아졌다.
2. **에이전트는 실행마다 편차가 크다.** 최종 실행의 5번 1라운드는 개선 없이 $0.34만 쓰고 멈췄다. 후처리가 그 상태에서도 점수를 0.81까지 내렸고, 2라운드(opus)가 이어받아 0.47까지 갔다.
3. **에이전트는 예산을 다 쓰지 않고 일찍 멈춘다.** 남은 예산으로 2라운드를 돌리는 것이 효과가 컸다.
4. **에이전트는 경고를 무시한다.** 쓰이지 않는 `simp` 인자나 deprecated 정리가 결과에 남는다. 지우는 것만으로 heartbeat가 준다.
5. **짧은 증명이 항상 싼 것은 아니다.** 10번에서 `rw` 두 줄을 `omega`로 바꾼 시도는 토큰이 13% 줄었지만 heartbeat가 1.2% 늘어 기각했다.

## 7. 우리 프로젝트에 적용할 점

- 하네스 = 주최 측 `cc_agent` + 결정적 후처리 + 남은 예산으로 재실행. 후처리는 LLM 비용이 0이다.
- 합격 판정은 명제 일치, 허용 공리, `sorry` 없음, 대상 정리 진단 0으로 둔다.
- 주최 측 `cc_agent`의 `tools/heartbeat.py`는 `omit … in`이 붙은 선언(10번)에서 측정에 실패한다. 측정 명령을 선언에 붙은 `omit`·docstring 앞에 넣도록 고쳐서 썼다. Lean 프로젝트가 `cc_agent/workspace` 밖에 있으면 lean-lsp MCP가 로드되지 않는 점도 주의한다.

## 8. 한계

- 에이전트는 API 키가 아니라 Claude Code 로그인으로 호출했다. 비용은 `cc_agent`가 정가로 기록한 값이다.
- 공식 평가 서버의 점수가 아니라 로컬 측정이다. 평가 서버가 같은 토큰 함수를 쓰는지는 확인하지 않았다.

## 9. 참고 자료

### 9-1. openai/math에서 가져온 것

[openai/math](https://github.com/openai/math)는 OpenAI의 AI 모델이 쓴 수학 논문 719편과, 그중 일부 결과를 Lean으로 증명한 코드를 모은 저장소다. 2026-10-07 버전(커밋 `fd4aeeb`)을 내려받아 파일을 직접 읽었다. 증명은 AI가 만들고 사람이 검토하지 않은 것이라(`review.status: unchecked`), 수학 내용의 정답이 아니라 **"Lean을 통과한 코드가 어떤 스타일인가"를 보는 표본**으로만 썼다. 이 저장소는 Lean v4.34.1을 써서 빌드하지는 않았다.

**① 증명 습관을 세어서 규칙을 만들었다.**

- 증명 코드 폴더 `lean/OAI`의 `.lean` 파일 122,458개 중, 목록에서 6번째마다 하나씩 뽑은 2만 개(433만 줄)를 셌다.
- 각 줄 맨 앞에 오는 증명 명령(tactic) 이름을 미리 정한 28개에 대해 셌다. 비율은 그 28개 합계를 100%로 놓은 값이다.

| 명령 | 하는 일 | 비율 |
| --- | --- | ---: |
| `have` | 중간 결과를 먼저 증명해 둔다 | 29.0% |
| `exact` | "이 정리가 바로 답이다"라고 근거를 직접 준다 | 26.2% |
| `rw` | 주어진 등식으로 식을 바꿔 쓴다 | 16.4% |
| `simp` | 아는 정리들을 대 보며 알아서 식을 정리한다 | 5.4% |
| `grind`, `aesop` | 증명 방법을 알아서 찾는다 | 0.0% (81회, 34회) |

- 정확히 지정하는 명령(`have`·`exact`·`rw`)이 71.6%이고, 알아서 탐색하는 명령은 드물다. 보조정리 374,597개 중 26%가 파일 안에서만 쓰는 `private` 보조정리로, 증명을 잘게 나눠 쓰는 습관도 보였다.
- 탐색하는 명령은 Lean이 여러 정리를 대 보느라 계산량(heartbeat)을 많이 쓴다. 대회는 이 계산량을 채점하므로, **"탐색 대신 정확히 지정"** 규칙을 만들었다.
  - **`simp?` 고정:** `simp`를 `simp?`로 바꿔 돌리면 Lean이 실제로 쓴 정리 목록을 알려 준다. 원래 `simp`를 그 목록만 쓰는 `simp only [...]`로 바꾼다. 5번에서 계산량이 23,681 → 16,026으로 줄었다.
  - **정리 이름 지정:** 부등식을 알아서 맞추는 `gcongr`를 `Nat.mul_le_mul_right` 같은 정확한 정리로 바꾼다. 10번에서 계산량이 약 1,200 줄었다.
  - 목록이나 이름을 적느라 토큰이 늘 수 있어서, 점수가 실제로 내려갈 때만 바꾼다.
- 한계: 줄 맨 앞만 셌으므로 `… <;> simp`처럼 줄 중간에 나오는 명령은 빠졌고, 28개 밖의 명령은 계산에 들어가지 않았다. 정확한 통계가 아니라 경향을 보는 근사치다.

**② 통과 기준을 빌려왔다.**

- 이 저장소의 `lean/ComparatorChallenges/`에는 Lean 공식 검사 도구 Comparator의 설정 파일 416개가 있다. 각 파일은 증명이 원래 문제를 정말로 증명했는지 확인하는 기준을 정한다.
  - `challenge_module`: 명제만 적고 증명은 비워 둔(`sorry`) **문제지**
  - `solution_module`: 실제 증명이 있는 **답안지**
  - `theorem_names`: 비교할 정리 이름
  - `permitted_axioms`: 증명이 기대도 되는 **기본 가정(공리)**. 416개 모두 `propext`, `Quot.sound`, `Classical.choice` 세 개다.
- 세 공리는 Mathlib 전체가 쓰는 표준 가정이다. `propext`는 서로 동치인 명제를 같은 명제로 보고, `Quot.sound`는 같다고 묶은 것은 실제로 같다고 보며(함수 외연성이 여기서 나온다), `Classical.choice`는 존재하면 하나를 고를 수 있다고 본다(배중률이 여기서 나온다). 이 밖의 공리가 보이면 반칙이다. 특히 `sorryAx`는 증명 어딘가에 `sorry`(증명 생략)가 있다는 표시다.
- Comparator 자체를 돌리지는 않았고, 같은 세 기준을 직접 검사했다.

| Comparator 기준 | 5·10번에서 한 검사 |
| --- | --- |
| 명제가 같다 | 수정본의 명제가 대회 데이터 `statement`와 글자까지 같은지 비교하고, 원본과 수정본의 `#check` 출력(Lean이 이해한 명제)이 같은지 비교 |
| 허용 공리만 쓴다 | `#print axioms` 결과가 정확히 `[propext, Classical.choice, Quot.sound]`인지 확인 |
| `sorry`가 없다 | 공리 목록에 `sorryAx`가 없는지 확인 |

**③ openai/math에서 오지 않은 규칙.** 쓰이지 않는 `simp` 인자 제거(Lean의 경고를 보고 지움)와 `calc` 단계 합치기(식만 다시 적는 단계를 다음 단계에 흡수)는 5·10번을 직접 고치며 찾았다.
