CrAn은 무엇일까?

CrAn은 Creation(크리에이션, 생성)과 Annihilation(어나일레이션, 소멸)의 약자입니다. 편하게 “씨알 에이엔”이라고 읽습니다. Field는 장, Op는 Operator(연산자)입니다.

𝓕.CrAnFieldOp는 생성·소멸 부분을 구분한 장 연산자의 타입입니다. PhysLib에서는 기본 장 연산자에 해당 부분을 구별하는 정보를 붙입니다. 위치 연산자는 생성과 소멸 부분을 구분하고, 점근 연산자는 허용되는 부분이 하나로 정해져 있습니다.

φ ψ : 𝓕.CrAnFieldOp
-- 파이와 프사이는 에프의 생성·소멸 장 연산자 타입에 속한다.

φ가 반드시 생성, ψ가 반드시 소멸이라는 뜻은 아닙니다. 물리적으로 생성·소멸 연산자는 입자 수를 하나 늘리거나 줄이는 역할로 이해할 수 있습니다.

03 / Strata · Core.InitsUpdatesComm

기존 칸을 바꾸고,
빈 칸을 채운다.

갱신 후 초기화한 실행이 주어졌을 때, 초기화를 먼저 해도 같은 최종 상태에 도달할 수 있을까?

갱신 · Update

이미 정의된 변수 x의 저장 내용을 바꿉니다. 대상 이외의 변수는 그대로 유지합니다.

x : 1 → 2

초기화 · Init

아직 정의되지 않은 변수 y에 처음 내용을 저장합니다. 대상 이외의 변수는 그대로 유지합니다.

y : 없음 → 10

두 실행 순서 따라가기

숫자는 설명용 저장 내용입니다. 실제 타입의 저장 대상은 P.Expr(표현식)입니다.

시작 σx=1 · y=없음
갱신 후 σ′x=2 · y=없음
최종 σ″x=2 · y=10

x를 갱신한 뒤 y를 초기화합니다. 두 순서의 최종 상태는 같습니다.

가정과 목표

UpdateStates σ ks vs σ′ →
InitStates σ′ ks′ vs′ σ″ →
∃ σ₁,
  σ₁ = updatedStates σ ks′ vs′ ∧
  InitStates σ ks′ vs′ σ₁ ∧
  UpdateStates σ₁ ks vs σ″

ks / vs는 갱신할 변수·저장 내용 목록, ks′ / vs′는 초기화할 목록입니다. 처음 주어진 경로는 σ → 갱신 → σ′ → 초기화 → σ″. 목표는 σ → 초기화 → σ₁ → 갱신 → σ″인 중간 상태 σ₁을 구성하는 것입니다.

함수와 관계를 구분하기. updatedStates σ ks vs는 새 상태를 반환하는 함수입니다. UpdateStates σ ks vs σ′는 두 상태 사이에 유효한 갱신 관계가 성립한다는 명제입니다. 함수 자체는 갱신·초기화의 유효 조건을 검사하지 않습니다.

왜 두 목록이 겹칠 수 없을까?

갱신 대상은 이미 정의되어 있고, 갱신 후에도 정의되어 있습니다. 그 뒤 초기화할 대상은 미정의여야 합니다. 따라서 같은 변수가 두 목록에 모두 속할 수 없습니다. 갱신은 미정의 변수를 새로 정의하지 않으므로 초기화 대상은 시작 상태 σ에서도 미정의입니다.

같은 x를 갱신한 뒤 초기화할 수 있을까?

이 정의의 두 실행 가정을 함께 만족할 수 없습니다. 갱신 후 x에는 값이 있는데, 초기화는 x가 미정의일 것을 요구합니다.

원본 → 수정본: 논증의 단위를 바꾸기

원본: 갱신 하나씩 교환

induction Hup generalizing σ''로 갱신 관계에 귀납합니다. 빈 목록과 첫 갱신·나머지 갱신을 나누고, 각 단계에서 초기화와 교환합니다.

수정: 전체 교환 정리를 재사용

두 대상 목록이 서로소임을 확보하고, updatedStatesComm으로 목록 전체의 변경 순서를 교환합니다. 이 기존 정리 내부에는 귀납법이 있습니다.

224원본 →133전체 정리 재사용 →90목표에 직접 재작성

133토큰 단계에서 이미 전략이 바뀌었습니다. 90토큰 단계에서는 긴 중간 교환 등식을 없애고, 정의를 펼쳐 목표에 기존 정리를 직접 적용했습니다. 후속 지역 이름 단축은 90토큰을 유지합니다.

구조 개선본 전체 코드
실제 Lean 코드 · 줄 번호를 지정해 질문할 수 있습니다
theorem InitsUpdatesComm
  {P : PureExpr} {σ σ' σ'' : SemanticStore P}
  {ks ks' : List P.Ident} {vs vs' : List P.Expr} :
  UpdateStates σ ks vs σ' →
  InitStates σ' ks' vs' σ'' →
  ∃ σ₁,
    σ₁ = (updatedStates σ ks' vs') ∧
    InitStates σ ks' vs' σ₁ ∧
    UpdateStates σ₁ ks vs σ'' := by
  intro hu hi
  have hn := UpdateStatesNotDefMonotone' (InitStatesNotDefined hi) hu
  refine ⟨_, rfl, updatedStatesInit (InitStatesLength hi) hn (InitStatesNodup hi), ?_⟩
  rw [InitStatesUpdated hi, UpdateStatesUpdated hu]
  unfold updatedStates
  rw [updatedStatesComm]
  · exact updatedStatesUpdate (UpdateStatesLength hu)
      (updatedStatesDefMonotone (UpdateStatesDefined' hu))
  · rw [List.unzip_zip (UpdateStatesLength hu), List.unzip_zip (InitStatesLength hi)]
    intro k hk hk'
    simpa [hn k hk'] using UpdateStatesDefined' hu k hk

수정 코드의 다섯 단계

  1. have hn := ...: 초기화 대상이 원래 σ에서도 미정의임을 확보합니다.
  2. refine ⟨_, rfl, ..., ?_⟩: 초기화를 먼저 한 상태를 제시하고, 등식과 초기화 유효성을 해결합니다. ?_는 이어서 증명할 갱신 목표입니다.
  3. rw [InitStatesUpdated hi, UpdateStatesUpdated hu]: 실행 관계에서 얻은 최종 상태를 함수식으로 표현합니다.
  4. unfold updatedStates; rw [updatedStatesComm]: zip한 목록에 대한 내부 함수를 드러내고, 전체 교환 정리를 적용합니다.
  5. updatedStatesUpdate로 갱신 유효성을 복원하고, List.unzip_zip으로 서로소 조건을 원래 변수 목록에 연결합니다. 겹치는 변수는 none이면서 some이어야 하므로 모순입니다.

theorem InitsUpdatesComm
  {P : PureExpr} {σ σ' σ'' : SemanticStore P}
  {ks ks' : List P.Ident} {vs vs' : List P.Expr} :
  UpdateStates σ ks vs σ' →
  InitStates σ' ks' vs' σ'' →
  ∃ σ₁,
    σ₁ = (updatedStates σ ks' vs') ∧
    InitStates σ ks' vs' σ₁ ∧
    UpdateStates σ₁ ks vs σ'' := by
  intros Hup Hinit
  exists (updatedStates σ ks' vs')
  have Hk : (isDefined σ' ks) := UpdateStatesDefined Hup
  have Hlen1 := InitStatesLength Hinit
  have Hlen2 := UpdateStatesLength Hup
  induction Hup generalizing σ''
  case update_none =>
    simp_all
    apply And.intro
    refine updatedStatesInit Hlen1 ?_ ?_
    exact InitStatesNotDefined Hinit
    exact InitStatesNodup Hinit
    simp [InitStatesUpdated Hinit]
    constructor
  case update_some σ x v σ₀ xs vs σ₁ Hup Hups ih =>
    refine ⟨rfl, ?_, ?_⟩
    . apply updatedStatesInit Hlen1
      apply UpdateStateNotDefMonotone' ?_ Hup
      apply UpdateStatesNotDefMonotone' ?_ Hups
      exact InitStatesNotDefined Hinit
      exact InitStatesNodup Hinit
    . apply UpdateStates.update_some (σ':=updatedStates σ₀ ks' vs')
      . simp [UpdateStateUpdated Hup, updatedStates]
        rw [← updatedStateComm']
        . have Hdef := UpdateStateDefined' Hup
          simp [isDefined, Option.isSome] at Hdef
          split at Hdef <;> simp_all
          next val heq =>
          apply updatedStateUpdate (v':=val)
          apply InitStatesSomeMonotone heq
          apply updatedStatesInit
          . simp_all
          . apply UpdateStateNotDefMonotone' ?_ Hup
            apply UpdateStatesNotDefMonotone' ?_ Hups
            apply InitStatesNotDefined Hinit
          . exact InitStatesNodup Hinit
        . rw [List.unzip_zip] <;> simp_all
          have Hnd := InitStatesNotDefined Hinit
          simp [isNotDefined, isDefined] at *
          apply Not.intro
          intros Hin
          specialize Hnd _ Hin
          simp_all
      . apply (ih Hinit ?_ ?_).2.2
        . simp [isDefined] at * <;> simp_all
        . simp_all

교환자 덩어리를
정렬 밖으로 꺼내기.

같은 시간 정렬 등급의 두 연산자 사이 교환자를, 주변 식의 시간 정렬에서 앞으로 분리합니다.

식에 등장하는 네 가지 대상

대상역할
φ, ψ (파이, 프사이)양방향 시간 정렬 관계를 만족하는 두 기본 연산자. 위치 연산자의 시간 비교로 보면 같은 시간입니다.
a, b (에이, 비)교환자 앞뒤에 놓이는 임의의 자유 대수 원소. 연산자 목록들의 선형 결합도 포함합니다.
𝓣ᶠ (티 위첨자 에프)목록을 시간 순서로 정렬하고 필요한 통계 부호를 곱하는 선형 함수. 단순한 곱셈 보존 함수로 취급하지 않습니다.
ι (이오타)정해진 교환 관계를 반영한 Wick 대수로 보내는 대수 준동형. 덧셈·곱셈을 보존합니다.

supercommutator · 슈퍼 커뮤테이터

두 기본 연산자 A, B에 대해 순서 차이를 통계 부호 ε와 함께 표현합니다. 여기서 ε는 엡실론이라고 읽습니다.

[A, B]s = AB − ε BA

ε=1이면 AB−BA, ε=−1이면 AB+BA입니다. 일반적으로 AB와 BA를 같다고 바꿀 수 없습니다. 코드의 ofCrAnOpF φ는 기본 연산자 φ를 자유 대수의 원소로 옮긴 것입니다.

문제를 한 식으로 읽기

ι(T(a · C · b)) = ι(C · T(a · b))

설명용 표기: C는 [ofCrAnOpF φ, ofCrAnOpF ψ]ₛF, T는 𝓣ᶠ입니다.

왼쪽은 교환자 C를 가운데 둔 전체 식을 시간 정렬하고 이오타로 보낸 결과. 오른쪽은 a·b를 시간 정렬한 뒤 C를 앞에 곱하고 이오타로 보낸 결과입니다. 등식은 Wick 대수로 보낸 결과에서 성립합니다.

hφψ : crAnTimeOrderRel φ ψ
hψφ : crAnTimeOrderRel ψ φ
-- 파이와 프사이가 양방향 시간 정렬 관계를 만족한다.

원본의 반복은 어디에 있었나?

원본은 b에 대한 span 귀납 안에서 다시 a에 대한 span 귀납을 합니다. 목록 기저 분기에서는 교환자를 펼쳐 나온 [φ, ψ]와 [ψ, φ]의 주변 정렬 블록을 긴 calc에 반복해서 적습니다. 교환자를 제거한 빈 목록의 경우도 같은 주변 분해가 필요합니다.

전략 1 · 두 원소에 대한 귀납을 함께

induction Basis.mem_span ofCrAnListFBasis a,
  Basis.mem_span ofCrAnListFBasis b using
  Submodule.span_induction₂

Basis.mem_span으로 a와 b가 기저가 생성하는 공간에 속한다는 증거를 얻습니다. span_induction₂는 두 원소를 함께 처리합니다. 목록 기저끼리의 경우를 핵심 계산으로 삼고, 나머지 영·덧셈·스칼라배 분기는 선형성으로 해결합니다.

전략 2 · 바뀌는 가운데 목록을 매개변수로

    ι 𝓣ᶠ(a * [ofCrAnOpF φ, ofCrAnOpF ψ]ₛF * b) =
    ι ([ofCrAnOpF φ, ofCrAnOpF ψ]ₛF * 𝓣ᶠ(a * b)) := by
  induction Basis.mem_span ofCrAnListFBasis a, Basis.mem_span ofCrAnListFBasis b using
    Submodule.span_induction₂
  · rename_i hx hy
    rcases hx with ⟨as, rfl⟩
    rcases hy with ⟨bs, rfl⟩

목표: 어느 시점 이후 같은 패턴

∃ N c : ℕ, c > 0 ∧ ∀ n ≥ N, u (n + c) = u n

어떤 시작 위치 N 이후에는 양의 간격 c만큼 이동해도 같은 값입니다. 처음부터 주기적일 필요는 없습니다.

한 항 대신, 네 항을 기억하는 이유

u(i)=u(j)만으로는 다음 항이 같다고 할 수 없습니다. 계산에 필요한 나머지 세 항이 다를 수 있기 때문입니다. 다음 값을 결정하기에 충분한 정보를 하나로 묶습니다.

S(n) = (u(n), u(n+1), u(n+2), u(n+3))

같은 상태에서 출발하면, 같은 다음 상태로

점화식의 정보 흐름을 보여 주는 설명용 모형입니다. F는 직전 네 값으로 다음 값을 계산하는 규칙이며, 수열의 수치 해를 실행하지 않습니다.

i에서 시작하는 경로S(i) = (p, q, r, s)
j에서 시작하는 경로S(j) = (p, q, r, s)

두 위치의 네 항이 모두 같습니다. 두 경로의 다음 값은 같은 규칙으로 결정됩니다.

유한한 상태와 비둘기집 원리

각 항은 유한한 정수 구간에 있으므로 네 항 상태의 종류도 유한합니다. 상태는 S(0), S(1), S(2), …로 끝없이 이어집니다. 따라서 어떤 i<j에서 S(i)=S(j)인 두 위치가 있습니다. 이후의 상태도 같으므로 j−i가 주기가 됩니다.

세 문제에서 얻은 다섯 가지 인사이트

  1. 수학적 구조를 먼저 본다.

    전체 목록 교환, 두 원소의 공동 귀납, 네 항의 유한 상태가 각각 증명을 줄이는 핵심이었습니다.

  2. 정리를 적용할 수 있는 표현으로 바꾼다.

    3번의 unfold, 6번의 공통 블록, 13번의 인덱스 정리는 기존 정리와 목표를 연결합니다.

  3. 자동화의 범위와 방향을 제어한다.

    6번의 smul_comm 반복 재작성은 실패했습니다. 필요한 규칙만 지정하고, 교환 규칙은 적용 방향을 확인합니다.

  4. 이름 단축과 구조 개선을 구분한다.

    지역 이름 단축으로 세 문제 본문이 총 91자 줄었지만 당시 토큰 합계 800과 scaled heartbeat는 같았습니다. 13번의 260→259는 이후 별도의 타입 명시 표현 개선입니다.

  5. 실패·유지·측정 조건까지 전략으로 남긴다.

    더 짧지만 비용이 큰 후보, 타입 추론 실패, 기존 후보 유지도 탐색 결과입니다. 13번은 같은 프로세스의 후속 선언에 캐시 효과가 있어 독립 프로세스 측정으로 비교했습니다.
